# itsybitsy implementation notes

**Staged rollout scope:** default-enabled kernel wrapping described here applies to ordinary repository agents and per-repository coordinators, with per-type overrides. Enabled mode combines the itsybitsy `sandbox-exec` profile and proxy with the resolved path configuration and agent-type hooks. Disabled mode omits the itsybitsy wrapper/proxy/collector and restores pre-sandbox process behavior, but every CLI remains hook-authorized and prompt-free. The global `@system` coordinator remains unsandboxed; its launch, ownership records, and cleanup changes are deferred. See [SANDBOX-ROLLOUT.md](SANDBOX-ROLLOUT.md) for migration steps and validation limits.

Field guide for finding code. SPEC.md is the authoritative behavioral spec; this file points at modules and calls out non-obvious wiring. When a section overlaps SPEC.md, that section is the source of truth.

Runtime paths, tmux names, retained refs, prompt tags and agy names are centralized in `src/runtime-names.ts`.

## Per-agent message-delivery queue (`src/outbox.ts`)

Serializes tmux writes to a single agent so two near-simultaneous sends don't interleave their `send-keys -l` chunks + `Enter` into one merged prompt. See SPEC.md §4.1.1 and §8.5.

- **Queue**: `outbox.jsonl` under `~/.itsybitsy/agents/<machine>/<repo>/<agent>/` for agents with a stored key, reachable across agents so cross-agent `ib send` works — the coordinator home holds the centralized state (outboxes, team channels, teams.json). Codex spawns still pass `--add-dir <coordinatorHome>` (plus git-common-dir + parent-repo subdirs) in `buildCodexLaunchArgs`. They always use `-a never`; enabled kernel mode selects `-s danger-full-access` so Seatbelt supplies the process boundary, while disabled mode keeps Codex's own sandbox through the inline `itsybitsy_agent` permission profile (no `-s`; see the codex-spawn bullet below). The agent's own meta/log/state still live in the per-worktree dir; `newAgent` uses the strict registry snapshot and `fullyQualifiedAgentId` to write `meta.queue_key` at spawn. An unregistered repo uses the segment `~<repoId>`. `agentOutboxDir(agent)` uses the stored key for the agent’s lifetime. Agents without a stored key keep `~/.itsybitsy/agents/<agent>/` so already-running watchdogs can deliver their messages. Same-ID legacy agents in different repos share the flat queue. The directory holds the queue, its lock, and Claude’s statusline rate-limit record. Atomic writes may also leave `outbox.jsonl.tmp` and `claude-rate-limits.json.tmp.<pid>`. `OutboxMessage = {id, message, fromAgent, raw, enqueuedAtMs}`. For a stored key, `enqueueOutbox` appends only under the existing reservation. A send to a retired recipient fails if its queue directory is gone. Legacy recipients and the system coordinator can create their queue directories on demand. `readOutbox` is FIFO and skips malformed lines. `rewriteOutboxRemoving(dir, deliveredIds)` does tmp+rename of the remainder and re-reads to preserve mid-drain appends, then unlinks when empty. `archiveAgent` first calls `deleteClaudeRateLimits` to remove the usage record and its temporary files, then `deleteAgentOutbox` to remove the queue, temporary queue, and lock before removing the directory. Retire, merge, and nuke report unlink failures as warnings after finishing teardown. A fresh spawn reserves the queue leaf exclusively and releases it on failure.
- **Lock**: `.outbox.lock`, advisory via `open(path, "wx")` (O_CREAT|O_EXCL). `acquireOutboxLock` retries with backoff to ~5s, writes a `<pid>:<uuid>` body (the uuid is an ownership token). `steal` removes a stale lock (mtime > 30s) — set by the inline fallback, never the drain. `releaseOutboxLock`/steal only `unlink` when the on-disk token matches (`unlinkIfToken`), so a stolen-from holder never deletes the thief's lock. Always `releaseOutboxLock` in `finally`. There is one lock per queue directory. Keyless agents with the same ID share that lock across their tmux sessions.
- **`sendMessage` (ib-commands.ts)**: resolve sender (cwd-detect at ENQUEUE time via `resolveSenderId`) → `enqueueOutbox` to `agentOutboxDir(agent)` → if `hasLiveWatchdog(agentDir)` (fresh `meta.transient.json` `watchdog_pid` within `TRANSIENT_FRESH_MS` + `isPidAliveCtx` alive) return immediately (watchdog drains), else `drainOutbox(...,{steal:true})` inline. The hasLiveWatchdog check still reads from the per-worktree `agentDir` (meta.transient.json hasn't moved); only the queue dir is central. `opts.outboxDir` overrides the queue dir (used for the system coordinator, whose queue/lock still live in `getCoordinatorHome()` directly — that path was NOT moved into the central `agents/` subdir).
- **`deliverMessage(agent, queued)`**: the single tmux writer — has-session, view/copy-mode cancel (`cancelTmuxPaneModeIfActive`: probes `#{pane_in_mode}`, sends `send-keys -X cancel` only on a literal `1`, logs to agent.log), prefix format (`user.name` read, `BARE_RENDERED_SENTINELS`), chunked `send-keys -l`, length-scaled delay, `Enter`, recipient/sender logging, `writeAgentState("running")`. `drainOutbox` pops one at a time under the lock with a 250ms settle gap; removes a message only after its `Enter` succeeds (rewrite remainder) — no double-delivery, no loss. The mode cancel exists because a pane parked in tmux view-mode/copy-mode routes `send-keys` through the copy-mode key table (text is eaten or fails "no current client" via the `f`/`t`/`g` command-prompt bindings) — see docs/codex-cooked-tty-wedge.md "Second, separate failure".
- **Helper launch (`spawnHelperViaTmuxServer` / `buildTmuxHelperScript`, ib-commands.ts)**: the watchdog and `generate-summary` are started as `tmux run-shell -b '<wrapper>'` children of the unsandboxed tmux server (SPEC-SANDBOX §4C.2). The wrapper is mandatory, not cosmetic: a bare `run-shell -b` job that prints, exits non-zero, or is SIGTERM'd (the orphan-kill teardown does exactly that to every stopping agent's watchdog) makes tmux write a `terminated by signal 15` notice into the active pane of the most recently created/attached session and park it in view-mode — wedging an unrelated agent. The wrapper keeps the job's stdio empty, runs the helper as a waited child with its own log redirect, records a non-zero helper status as `[helper] exited rc=N` in that log, forwards a wrapper-directed SIGTERM to the helper, and always exits 0.
- **Watchdog (watchdog.ts)**: `runPerAgentWatchdog` drains at the top of every tick AND on an `fs.watch` event on the current queue directory (debounced 50ms, falls back to per-tick if `fs.watch` throws), coalesced so triggers don't pile up. Injectable via `setPerAgentDrain`/`resetPerAgentDrain`.
- **Agent addresses**. `resolveAgentTarget` in `src/resolve-target.ts` serves CLI operands and hook ownership checks. Pass the caller’s cwd. Repo comparisons use real paths through `src/repo-identity.ts`. A machine-wide search requires readable candidate directories. Rehire deduplicates archive matches by immutable id. `resolveSendTarget` applies the send-specific remote error and supports system and team destinations. The watchdog uses stored repo paths for manager and spawner notifications.
- **Remote agent cache**. The endpoint owner in `src/peers/service.ts` publishes poller changes through `src/peers/remote-agents.ts`. CLI lookups check the endpoint lock generation and owner before using a snapshot. Watch refreshes the lock timestamp each poll so a sandbox that cannot read process start times can check a short lease.
- **Watchdog tick = one tmux client**: `observeTickTmux` → `captureTmuxWithPaneState` (`src/tmux-poller.ts`) runs `list-panes -s ; display-message ; capture-pane` as one tmux command sequence; the nonce/end-marker parse and the measured `;` failure behavior are in its comment. A non-zero exit is a capture error → `probeTmuxSessionFn` (`has-session`). The test seams `setPerAgentCaptureTmux` / `setPerAgentProbeTmuxPane` switch `observeTickTmux` to the two separate calls, so lifecycle tests script each result; leave both reset to exercise the real one-call path (the spawn-count tests in `watchdog.test.ts` do, with a fake tmux on `tmuxPollerSpawnCtx`). Handlers get the tick's capture as the 4th `StateHandler` argument (`tickOutput`); `handleWaiting` reads its background-shell check from it and only the test-only `tick()` path, which passes none, captures again. The notification snapshot (`makeLazyAllAgents` → `loadAllAgentsForNotification`) reads `readAgentsOfRepos` — disk only, because `readAllAgents` would also spawn `tmux list-sessions` for an orphan list the watchdog never reads.
- **Coordinator/hook paths**: `sendToSystemCoordinator` passes `outboxDir: getCoordinatorHome()`; BOTH dashboard system-coordinator send paths route through it — the `s`-key dialog (`handleSendToCoordinator`) and the inline coordinator input field (`coordinatorInputField.onSubmit`). Both first intercept a trimmed exact `/restart`/`/respawn` (via `isCoordinatorRestartCommand`) and call `restartSystemCoordinatorFresh()` (discard→ensure→wait-for-ready, cleared marker → NO resume) instead of the verbatim send — parity with the Telegram `/restart` dispatch (`dispatchSlashCommand`, whose injectable `restartCoordinatorCtx` defaults to the same helper). Contrast the `R` key = `restartSystemCoordinator()` (resume). `hooks/agent-status.ts` routes self-nudge / `notify_manager` through `sendMessage` with `fromAgent: WATCHDOG_SENTINEL` → delivered as `[sent by watchdog]:` (so the recipient can tell a system nudge apart from a human console send).
- **Watchdog direct writes**: the watchdog's own direct keystrokes (rate-limit-bypass Enter, and the startup permission auto-accept) bypass `deliverMessage` and the file lock, so they're serialized against the fs.watch-driven drain by a per-agent in-process async mutex `runSessionExclusive(agentId, fn)` (promise-chain keyed by id — `tick()` never cross-blocks agents). BOTH the drain and every direct write run inside it.
- **Startup permission auto-accept (prompt-specific, not a bare Enter)**: `classifyClaudeStartupPrompt(output)` in `src/coordinator.ts` is the single shared detector, imported by `watchdog.ts` and the resume/new-agent helpers in `ib-commands.ts`. Claude Code 2.1.259 rebuilt workspace-trust / external-import on a shared confirmation component with `cancelFirst:true` + `focus:"cancel"` — the cursor defaults to the cancel option, so a bare Enter on the trust prompt selects "No, exit" and QUITS Claude. Binary-confirmed accept sequences: trust & external imports → `Down,Enter`; single new MCP (`defaultFocusValue:"no"`, last option) → `Up,Up,Enter`; multi-MCP checklist (all preselected + "Enable selected" submit) → `N Downs,Enter`; all pre-2.1.259 layouts → bare `Enter`; generic tool/Bash → null (never accepted). New-trust detection requires co-presence of "No, exit" + "Yes, I trust this folder" + "Enter to confirm"; the agy trust card (guide reads "enter Confirm", no "to") is excluded and keeps its own bare-Enter fallback. The whole sequence goes out in ONE `send-keys` call (keys stay in order, no interleave); this does NOT by itself guarantee the keys share one side of Claude's ~150ms input-refusal window — the safety is the authoritative **visible-pane** re-capture (`-S 0 -E -`, no scrollback) + re-classify done immediately before the send (coordinator under the outbox lock, watchdog under `runSessionExclusive`), plus the ≥poll-interval settle before retry. In the watchdog, the under-mutex re-check returns whether a sequence was actually sent; if the tick capture classified a prompt only from stale history, nothing is sent and the loop falls through to normal state processing rather than sleep+continue (so a phantom prompt in the history window can't starve state handling).

## State detection

Deterministic model. See SPEC.md §1.3.

1. Stop hook (`ib hook-status`) writes `state` to `meta.json` when Claude goes idle (`waiting`, `complete`, or `running`).
2. `ib send` and `ib resume` write `state: "running"` to `meta.json`.
3. `detectAgentStates()` reads state from meta.json with tmux overrides for compacting / rate_limited / api_error / api_terms / api_safeguard / stopped.
4. `MetaState` = `"creating" | "running" | "waiting" | "complete" | "stopped"` (stored). `AgentState` (parse-state.ts) is the broader union that adds `compacting`, `rate_limited`, `api_error`, `api_terms`, `api_safeguard`, and `unknown` for runtime overrides.
5. `creating` is also derived from `created_epoch` (< ~6s ago) when the meta state would otherwise be ambiguous.
6. `api_error` is an override surfaced via `isApiError(tmuxOutput)` and the `tmux_api_error` flag in `TransientState`. Two TERMINAL siblings sit next to it, both checked BEFORE `api_error` (terminal-before-recoverable) and both no-op in the watchdog (never retried): `api_terms` (a genuine Usage-Policy/AUP refusal — `isApiTerms` / `tmux_api_terms`) and `api_safeguard` (a model input-safety rejection, e.g. Fable's "safeguards flagged this message"; often a probabilistic false positive — `isApiSafeguard` / `tmux_api_safeguard`; remediation is edit-the-message or switch-model, not retry).
7. `parseState()` is retained as legacy for the bash ib reference and the watchdog's rate limit bypass retry loop.
8. Codex agents reach the same `MetaState` via their hooks (SessionStart → running, UserPromptSubmit → running unless stopped, Stop → waiting/complete). Existing terminal captures also detect usage limits (`rate_limited`) and the current `■ exceeded retry limit, last status: 429 Too Many Requests` or `■ Selected model is at capacity. Please try a different model.` banner (`api_error`, guarded by a Codex status footer). The latter works even without a Stop hook through `isCodexApiError`, shared by `isApiError` and the snapshot parser; the watchdog persists it in `tmux_api_error` for dashboard readers. Codex/Fugu automatic retry remains disabled. Compaction and other API-error patterns remain deferred (SPEC-CODEX-MODEL.md §5.6).
9. agy agents reach `MetaState` via their hooks too (PreInvocation → running, Stop → waiting/complete). The tmux fallback/override parser is `parseAgyState` / `isAgyTmuxOutput` in `parse-state.ts` (`esc to cancel` / Braille spinner → running; trust card → creating; `? for shortcuts` or bare `>` between separators → waiting; sentinels as elsewhere). `rate_limited`/`api_error`/`compacting` stay `unknown` for agy (strings not captured yet); the claude-shaped override detectors don't false-positive on agy panes.

## TUI

- **Remote system coordinator** (`src/tui/agent-tree.ts`, `src/tui/remote-pane.ts`). Peer coordinator rows use the peer id for selection. The tree reserves space for the colored link word before sizing the italic machine name and shows the last successful poll's age on dimmed offline rows when known. The row model retains the reported coordinator state for the info panel. The dashboard routes these rows through the remote action guard. Its pane component, `RemotePane`, which also shows remote agent captures, owns the selection timer, tracks pending reads by peer id across selection changes, slices the coordinator's input box off the last successful capture (`computeChromeSlice` with the Claude detector, as for the local coordinator; an agent's capture is left whole, since its CLI is not reported), and wraps the transcript at the full main width. Its `statusLines()` returns the CLI's status lines, which the dashboard draws below its own input field. A visible dialog pauses reads. A selection change discards late results. The dashboard's peer-service listener also applies changes to the startup caller decision.
- **Remote agent prompt** (`src/tui/remote-prompt.ts`, `src/peers/agent-pane.ts` `readAgentPromptText`; SPEC.md §20.5). `RemotePrompt` is `RemotePane`'s counterpart for INITIAL PROMPT on a remote agent row. `syncRemotePane` selects it only while that mode shows the agent with no dialog; it reads through `PeerService.fetchAgentPrompt` (the `agent-prompt` request) at once and every `REMOTE_PROMPT_REFRESH_MS`, and caches each agent's last prompt by its `currentAgentKey`. The dashboard's callback drops a result for an agent no longer selected and otherwise sets `rightPane.promptContent`, so the right pane draws it as it draws a local prompt. `rightPane.remoteAgent` makes that pane say `Loading prompt.txt...` rather than `No agent selected` before the first answer.

- **SplitPane (`src/tui/split-pane.ts`)**: pi-tui's `Box` is vertical-only. `SplitPane` renders two child components side-by-side by calling each child's `render(width)` independently, then merging lines: left is padded to exact width, separator char inserted, right is truncated.
- **TmuxPoller (`src/tmux-poller.ts`)**: polls only the SELECTED target at ~1s via `setInterval`. The dashboard runs three: selected agent, system coordinator (`ib-coordinator`), and currently selected per-repo coordinator. `setAgent(session)` switches target. Race guard: snapshots `targetSession` before async `Bun.spawn`, discards result if target changed during await. `captureTmuxOutputResult()` is the separate one-shot export used by `detectAgentStates()` in the watcher — it preserves the stderr/spawn detail an unknown observation needs. (`captureTmuxOutput()` is the older nullable wrapper, still used by the watchdog's event-time handlers; the watchdog tick itself uses `captureTmuxWithPaneState()`, capture + pane-dead probe in one tmux client.)
- **Line wrapping (`src/tui/wrap.ts`)**: `wrapSingleLine`/`wrapLines` (ANSI-aware hard wrap) and `wordWrapSingleLine`/`wordWrapLines` (break at spaces, hard-wrap over-width tokens). The tmux panes reflow the `-J` logical capture to the display width via `wordWrapLines`, memoized per (raw, width) by `WordWrapCache`. `computeChromeSlice(raw, isCodex, isAgy=false)` splits the capture into transcript + input-box chrome by detecting the chrome on the **UNWRAPPED logical lines** (`findLastTwoSeparators` for Claude, `findCodexInputChromeLogical` for codex, `findAgyInputChromeLogical` for agy — the last two `────` separators guarded by an agy status line, with a no-trim fallback) — this is the crux of the pinned-width design (see below): a pinned-width separator is a single ~1000-col logical line, so detecting after wrapping would explode it into many rows and mis-slice. `isCodex`/`isAgy` are mutually exclusive; callers set only the flag matching the agent.
- **Links in tmux panes (`src/hyperlinks.ts`)**: Ghostty's plain-text link detection has a fixed scheme list with no `message:`, and a Markdown link captures as only its label, so `TmuxPoller.poll()` handles both. It captures with `-e`, because that is the only way to read a link's target out of tmux. `keepAllowedLinks` then drops all styling, so panes still render uncolored, and keeps only OSC 8 links whose target is `message:`, `http:` or `https:`. Other targets keep their label but lose the link, because the label hides where the click goes and the click runs outside the agent's sandbox. `linkifyMessageUrls` wraps bare `message://` URLs. The poller's delivery dedupe compares the filtered text, so a color-only change costs no render. `wordWrapSingleLine` runs `balanceLinkRows` per logical line, so a link split across rows is closed and reopened on each row, stays clickable, and can't spill into later rows or the column to its right; its clip paths use `closeOsc8` because `truncateToWidth` drops a link's close sequence. Limit: an over-width table is reflowed from ANSI-stripped cells (see `reflowTable`), so links inside it are lost. State detection captures are separate and stay plain.
- **Pinned tmux width (`PINNED_TMUX_WIDTH` in `src/tui/widths.ts`)**: every agent AND coordinator tmux window is pinned to 1000 cols and NEVER resized to follow a display pane — because `capture-pane -J` can't un-wrap a TUI's own hard `\n`, so any window resize repaints the whole transcript into scrollback. `tmuxWidthForAgent()` returns `PINNED_TMUX_WIDTH` for both; spawn/resume/coordinator-create all route through `getTmuxWidthForAgent()`. There is NO `onWidth` poller callback and NO on-select / divider-drag / sidebar-resize / SIGWINCH tmux resize — those were removed. `splitPaneLeftWidth`/`mainWidth` are DISPLAY-only (reflow + divider position). A one-time re-pin migration (`requestTmuxRepin()` → `pendingTmuxResize` on first populated `onUpdate`) resizes existing agent + coordinator windows to the pin; Ghostty detach re-pins via `checkClientAttached`. **Deliberate asymmetry**: the per-repo coordinator pane (`pane-manager.ts renderRepoCoordinatorSection`) never did chrome detection — it word-wraps the full capture and shows the coordinator's raw input box — so it is left as-is (no mis-slice to fix); only `TmuxPaneComponent` (center + system-coordinator panes) and `RemotePane` (for a peer's system coordinator only) trim chrome. See SPEC.md §13.8.
- **Pane widths**: single source of truth in `src/tui/widths.ts`. Spawn/resume code uses the async `getSaved*` / `getTmuxWidthForAgent` helpers; dashboard render uses the sync `getLive*` wrappers (or `DashboardComponent.getMainWidth()`). Per-repo coordinators render at `mainWidth`, same as the system coordinator. **Never compute pane widths inline.** Formula: `mainWidth = terminalWidth - sidebarWidth - 1`.
- **Layout persistence**: panel sizes saved to `~/.itsybitsy/layout.json` via debounced write (500ms). Restored on startup with validation (rejects NaN/Infinity, clamps the widths to valid ranges; `heightOffsets` load as saved — the sidebar render clamps a copy of them, and the `{`/`}` resize stores a clamped copy only when it changes a height, SPEC §13.3.1). Also holds the optional `pinnedRepoPaths` and `favoriteAgentIds` string lists (a malformed list is dropped, the rest of the layout still loads; `favoriteAgentIds` keeps only fully qualified ids, `isFullyQualifiedAgentId`, so an old bare id is dropped).
- **Dashboard (`src/tui/dashboard.ts`)**: three-column layout (resizable sidebar with agent tree + info panel | resizable tmux pane | cycling right pane). 5 focus targets in normal mode (`FOCUS_ORDER`): agent-tree, info, active-agent, right-pane, repo-coordinator. Tab/Shift+Tab cycles. `[`/`]` resize width (focus-aware), `{`/`}` resize sidebar panel height. Right pane modes (`PANE_MODES` order): PROXY LOG, WATCHDOG LOG, AGENT LOG, INITIAL PROMPT, DENIALS, TREE, ERRORS, DIFF, QUESTIONS, STATUS, REPO. Right pane mode is global state — persists across agent selection changes. `p`/`n` cycle pane modes (p=forward, n=backward). The startup pane is AGENT LOG, which is NOT index 0 — `modeIndex`/`savedModeIndex` start at `DEFAULT_MODE_INDEX` — so `n` from it reaches WATCHDOG LOG then PROXY LOG and `p` reaches INITIAL PROMPT. The three log modes (AGENT LOG → `agent.log`, WATCHDOG LOG → `watchdog.log`, PROXY LOG → `sandbox-proxy.log`) share one loader, `loadTailLog(ctx, agent, mode)` in `src/tui/pane-manager.ts`, driven by the `TAIL_LOG_SLOTS` table (mode → file name → its own `RightPaneComponent` content/window/loading fields, so modes never mix content). Each reads a tail window via `readAgentFileWindow` and skips the re-read while `statAgentFileSize` is unchanged and the cached window covers the view. The "No <file> found" / "<file> is empty" placeholders are cached too (`LogWindow.fileState`, keyed on stat null / 0), so an open PROXY LOG with the sandbox off costs one stat per sync; read-error and "line too long" placeholders are never cached. AGENT LOG loads on selection change; WATCHDOG LOG / PROXY LOG load from `triggerAsyncLoadIfNeeded` (mode entry + every dashboard sync, so they pick up growth while viewed). All three reload on scroll (`loadTailLogIfNeeded`) and on resize (`invalidateTailLogWindow`). Agent actions: `x` retire, `!` nuke, `R` resume, `r` reassign, `m` merge, `s` send, `a` new-agent. `;`/`l` scroll both panes simultaneously. See SPEC.md §11–13.
- **Info panel "Git Status" stoplight (`src/git-status.ts`, `src/tui/info-panel.ts`)**: fourth light under Tmux in agent mode — green clean / yellow dirty / grey unknown, read from `infoPanel.gitCleanliness`. The dashboard owns the probe: `refreshGitStatus()` runs `git -C <worktree> --no-optional-locks status --porcelain` through `gitStatusSpawnCtx` for the SELECTED agent only (`infoPanel.agent`, so team-member selections work too), fired once from the selection-change branch of `syncSelectedAgent` (which first resets the field to `null` so the light goes grey rather than stale) and then every 3s from `gitStatusTimer` (started/stopped with the other pollers). In-flight guard + selected-id race guard, same shape as `checkClientAttached`. Dirty = any porcelain line (untracked included) — the same rule as the `ib new-agent` gate. The same refresh also fills `infoPanel.gitHead` (`getWorktreeHead`) and `infoPanel.gitCommitCount` (`getCommitsSinceParent`: `git rev-list --count <parent>..HEAD`, parent = `agent/<meta.manager>` or `main`, the `ib status` rule), rendered as `(<hash>, N commits)`. The `bun test` preload sets the context's reset baseline to the safe stub (stdout "" → "clean"), because nearly every dashboard test reaches the probe.
- **Header Remote Control light (`src/remote-control-light.ts`)**: `readRemoteControlFiles()` reads "configured" (`loadAgentType("system-coordinator").remoteControl === true`, the call `ensureSystemCoordinator()` makes; a throw is false) and `settingsLaunched` (`systemCoordinatorSettingsPath()` in `src/coordinator.ts`, the file `writeCoordinatorFiles()` writes, is a regular file that parses to a JSON object without `disableRemoteControl: true`; opened `O_NONBLOCK` so a FIFO cannot hang it). No process is spawned. `remoteControlStatus(files, coordinatorStopped)` is pure: launched = `settingsLaunched && !coordinatorStopped`; both → green `on`, neither → hidden `off` (`light: null`), configured but not launched → yellow `stopped` or `pending-on`, launched but not configured → yellow `pending-off`. The stopped state is separate because a stop (`x`, an external kill) leaves the settings file in place. In the dashboard, `refreshRemoteControlStatus()` re-reads the files at startup, on every 5 s `statusLightTimer` tick, and once the not-awaited startup `ensureSystemCoordinator()` settles (`refreshRemoteControlAfterLaunch`); a call during a read makes that read run again. `onUpdate` feeds the watcher's `system-coordinator` entry to `noteSystemCoordinatorState`, which re-applies the light without IO. `isSystemCoordinatorStopped()` is true only after two watcher updates in a row said `"stopped"` (`coordinatorStoppedUpdates`; any other state or a missing entry resets it to 0). A launch leaves no session for well under a second and watcher passes run on a 2 s tick, so two stopped updates in a row mean the coordinator really is stopped; a stale stopped pass after a launch is followed by a running pass that resets the count. This holds for launches from any process, `ib respawn @system` included. `setRemoteControlStatus` renders only when the light changes (a missing status counts as hidden). The header draws it between Collector and Telegram; `?` help shows `remoteControlDetail()` (wrapped onto rows with an empty key) only while the light is shown. Seams: `DashboardComponent.remoteControlProbe` (`RemoteControlFilesOptions.loadSystemCoordinatorType` / `settingsPath`). See SPEC.md §15.5.2.
- **Sidebar tabs + favorites (`src/tui/sidebar.ts`, `src/tui/agent-tree.ts`)**: `1`/`2`/`3` set `sidebarMode` to `"agents"` / `"teams"` / `"favorites"` through `DashboardComponent.setSidebarMode` (the single writer — it also mirrors `focusManager.sidebarMode` and calls `agentTree.setFavoritesOnly`). Favorites is NOT a third tree: it is the Agents `AgentTreeComponent` with `favoritesOnly` on, so selection, focus target and `FOCUS_ORDER` are shared, and `activeSelectionSource` stays `"agents" | "teams"` (`SelectionSource`). The view shows the system coordinator plus favorites and their same-repo `meta.manager` descendants (`hasFavoriteInChain`; `meta.spawned_by` is not followed); with no agent row, `favoritesEmptyHint()` renders in an extra row under the coordinator, and `renderRowCount` (not `visibleList.length`) counts it so the sidebar and the `{`/`}` resize give the tree room for it. The filter lives in `visibleList` (`applyFavoritesFilter` → V filter → `dropAgentlessRepoHeaders` → `pruneEmptyParentHeaders` → `recomputeConnectorsForVisible`); the selected row is carved out from the selected id. `favoriteAgentIds` (fully qualified ids) lives on the Agents tree and persists in `layout.json`; the dashboard hands the set to `teamsTree` (before render) and `rightPane` (on each refresh) for the yellow ★ (`favoriteStar()`), and each checks it with `localAgentKey(machineName, agent)`. The `.` handler in `dashboard.ts` toggles a favorite (`agentTree.toggleFavorite(agentTree.agentKey(agent))`) or a pin (repo header) on the effective selection. ## Hooks (`src/hooks/`)

Native hook implementations run as Claude Code hook commands. Five fire inside spawned agent sessions; two fire in the primary Claude session that runs `ib watch`. Three additional codex-side hooks and three agy-side hooks exist (see the Codex and Antigravity CLI sections below).

Agent-session hooks:
- `hook-check-path <agentId>` → `agent-path.ts`: tool authorization and path isolation, **deny-by-default** (SPEC.md §6.1, SPEC-PATH-ALLOWLIST.md current implementation). It checks merged `permissions.deny` before `permissions.allow`, then emits an explicit allow or deny before Claude's native permission resolution; denied/unlisted calls are rejected and allowed calls do not prompt. An MCP tool matched by `toolsIgnoringPaths` (see "Agent types" below) is allowed right after the tool gate and the Bash branch, with no path extraction. After that tool gate and the structural steps (protected writes — the agent's own `meta.json`, and for `@system` its `agent-types/`/`config.json`/`repos.json`/`layout.json`/`sealed/`/`peer/`; other agents' dirs; the main repo), every file/`cd` path and every recognizable Bash path resolves through the **shared resolver** `resolvePreparedAccess()` (`src/sandbox.ts`) against the per-agent access table built by `paths-table.ts` — normalized `meta.paths` unioned with CLI-appropriate runtime roots. Supported kernel profiles use the corresponding table. A missing `paths` block gives all three lists empty; in a partial block, only omitted members default empty and populated entries remain enforced. Malformed stdin and an unreadable `meta.json` deny (fail-closed). `@system` has no `meta.json`, so its lists come from `_all.md ∪ system-coordinator.md` resolved live. Denials keep the `[PreToolUse] Permission denied:` prefix and append the operation, resolved path, and rule for the Denials tab. The Bash scanner is advisory rather than complete shell parsing. In particular, its general path-policy checks recognize `tee`, `cp`/`mv`, `mkdir`, and other common write destinations, but `@system`'s broad `~/.itsybitsy` runtime root permits those destinations; the separate protected-file guard covers file tools plus recognized redirects and `sed -i`, not every recognized write verb. That hook-only gap, dynamic shell constructs, and symlink races are accepted residuals.
- Hooks run inside the agent's kernel sandbox and must not open a path the agent may not read (SPEC.md §6.1 "Hook invariant"): each open is a kernel denial in the DENIALS view. Paths are canonicalized with `canonicalizeAccessPath()` (`src/sandbox.ts`), which is `canonicalizeSandboxPath()` unless the prepared table is marked `kernelSandboxed`, and then resolves symlinks with `lstat`/`readlink` and calls `realpathSync` only where an allow entry may match (`canonicalizeSandboxPathWithin()`). The hook-only structural checks in `agent-path.ts` (protected writes, other agents' dirs, the main repo) compare `structuralPath()`: with the sandbox on, the deepest existing prefix with the same dev+ino as one of their anchors takes the anchor's spelling, so a case, Unicode-folding or firmlink spelling of an existing directory that the canonicalizer kept cannot slip past them. Names that do not exist yet, relative traversal tokens and `name=/path` tokens are still compared by spelling (SPEC.md §6.1 known limits). `resolveBoundHookAgent()` (`agent-context.ts`) realpaths `<repo>/.itsybitsy/agents/<id>`, not the repo root in every mode (`locateRegisteredAgentDir()` falls back to the repo root only for a symlinked `.itsybitsy`, `agents` or `<id>` dir, or an id dir in another letter case), and, when every `worktree: false` record found has its sandbox on, passes only the repos of the records found for the id to `resolveNoWorktreeCaller()` (`deps.roots`). "Inside the sandbox" is `metaKernelSandboxed(meta)` (`src/sandbox.ts`, the frozen `meta.sandbox` policy), not `isSandboxedProcess()`: its `bun:ffi` load opens the macOS SDK directory, itself a kernel denial.
- `paths-table.ts` (imported by the three PreToolUse handlers, deliberately light — no `ib-commands.ts` import): `buildAgentAccessTable()` (worktree agents, from `meta.paths` and the agent CLI; inside the kernel sandbox — `metaKernelSandboxed()` — it uses the stored `meta.paths` as stored via `storedPathAccessTable()` and marks the table `kernelSandboxed`; outside it canonicalizes as for the profile; in every mode it passes the raw `tmuxSocketDirPath(uid)`, which the table builder canonicalizes like every runtime root; a build error denies with `accessTableDenyReason()`), `buildSystemHookPolicy()` (`@system`, from the `_all`/`system-coordinator` layer union: the access table plus `toolsIgnoringPaths`, each layer loaded once per call), `agentPathAccessTable()` (the sync core wrapping `sandboxPathAccessTable()`), and `pathDenialReason()` (the Denials-tab wording, using the resolver's own `orderedEntryMatches` so message and decision never disagree). The Claude project dir + scratchpad are appended only for Claude; `metadataCli()` treats legacy metadata with an absent model, a safe bare Claude model name such as `sonnet`/`opus`, or the `unknown` value produced by `readAgentMeta()` as Claude, while codex, fugu, and agy omit those roots, matching their kernel parameter sets. agy instead gets its own `AGYSTATEDIR` (`~/.gemini`, via `agyStateDirFor(home)`) as a write root, absent from the other tables. `tmuxSocketDirPath` / `resolveTmuxSocketDir` live in `src/sandbox.ts` so the hook can import `tmuxSocketDirPath` without pulling in `ib-commands.ts`.
- `hook-status <agentId>` → `agent-status.ts`: stop hook. Detects stuck agents and sends nudge messages. Debounced via timestamp file.
- `hook-permission-denied <agentId>` → `permission-denied.ts`: defense-in-depth PermissionRequest hook. Denies any request that reaches Claude's native permission layer and logs it to agent.log, so a native approval card is never delegated to the user. PreToolUse normally decides first.
- `hooks intercept-task` → `intercept-task.ts`: PreToolUse hook. Blocks disallowed models and unauthorized task spawning. Also denies busy-wait Bash (`sleep N`, `while`/`until` loops with `sleep`).
- `wait-hint.ts`: the busy-wait detector and the `WAIT_HINT` text that tells an agent to use `WAITING` instead of polling (SPEC.md §6.1 "Wait hint", §6.4). Coordinators get `COORDINATOR_WAIT_HINT` from `waitHintFor()`. The watchdog does not notify a coordinator about an agent it started in another repo, so this hint adds a `ScheduleWakeup`/`CronCreate` check-in step. `intercept-task.ts` uses both for its deny. `agent-path.ts` `emitPathDecision()` adds the hint only to the agent-facing reason when it denies a `Monitor` call or a busy-wait Bash command. The `agent.log` line and the Denials tab keep the short reason.
- `hooks session-start` → `session-start.ts`: SessionStart hook. Injects role-specific context. Loads type definition, interpolates the `_all` / `_non_coordinator` layer bodies and the type body with `{{variable}}` and `{{#if cond}}...{{/if}}` blocks; a type with an empty body gets only the layer bodies (no hardcoded fallback for typed agents). Legacy agents without `agentType` use role detection from the `worker` boolean and get the hardcoded manager/worker text. Size flag: Claude Code cuts a hook's `additionalContext` above 10,000 characters (`HOOK_CONTEXT_CHAR_CAP`) down to a 2,000-character preview, so `{{pathIsolation}}` and `{{availableTypes}}` render at a fixed size, and `flagOversizedInstructions()` logs to `agent.log` and raises a question for an agent that is still over (`askQuestion(..., { fromHarness: true })` in `ib-commands.ts`; SPEC.md §6.3.1).

Agent-session statusline (a `statusLine` setting, not a hook event):
- `hooks statusline <agentId>` → `statusline.ts`: the statusLine of every Claude session ib launches (`buildStatusLine` / `resolveUserStatusLine` in `src/settings-builder.ts`; SPEC.md §6.6.2). Records the input's `rate_limits` via `recordClaudeRateLimits` (`src/claude-rate-limits.ts`, `claude-rate-limits.json` in the agent's queue directory), then runs the user's own statusLine command (`statuslineRunnerCtx`) and prints its output. `readClaudeUsage` (same module; per-window `combineWindows` across the coordinator record, flat legacy records, and qualified agent records — the window with the latest `resets_at`, then the report of the record with the newest `updatedAt` in it, averaging same-second ties; not the highest report, since a manual limit reset lowers usage within a window; this relies on `recordClaudeRateLimits` skipping unchanged writes) is the only source of Claude plan usage for the dashboard and the watchdog — ib never reads the keychain. `archiveAgent` calls `deleteClaudeRateLimits` before `deleteAgentOutbox`, or the per-agent folder's rmdir fails.

Codex hooks (all dispatched through `codex-dispatcher.ts`):
- `hooks codex-pre-tool-use <agentId>` → `codex-pre-tool-use.ts`: PreToolUse handler — allow/deny + path isolation for Bash and apply_patch. Denies are checked before allows or paths. For apply_patch, the raw name and `Write`/`Edit` aliases participate in tool authorization: any corresponding deny blocks, while any corresponding allow admits the category. The handler then parses every patch target (`*** Add File:` / `*** Update File:` / `*** Delete File:`) and checks it as a write; any denied path rejects the whole patch. The mandatory default Write/Edit floor keeps normal agent patches available subject to path enforcement. Allow output MUST echo back `tool_input` as `updatedInput` (standalone allow fails open). Defaults to deny. Codex names MCP tools `mcp__<server>__<tool>` in `tool_name`, like Claude; `toolsIgnoringPaths` comes live from the type layers with the allow list (`loadCodexEffectivePermissions`).
- `hooks codex-session-start <agentId>` → `codex-session-start.ts`: writes `state: "running"` to meta.json; captures `meta.codex_session_id` on first firing (defensive read of both `session_id` AND `sessionId`); returns the agent's role text (`buildAgentRoleBody()`) as `additionalContext`.
- `hooks codex-user-prompt-submit <agentId>` → `codex-user-prompt-submit.ts`: writes `state: "running"` when a prompt is submitted, unless `stopped` (`markRunningOnPrompt`, shared with Claude's `hook-mark-running`); prints `{}`.
- `hooks codex-stop <agentId>` → `codex-stop.ts`: writes `state: "waiting"` or `"complete"` to meta.json — deterministic, no tmux scraping.
- `codex-dispatcher.ts` — fail-open-safe wrapper. NEVER throws; always exits 0 in production. Validates `<agentId>` before any other work; emits deny + `exit 0` on parse / module-import failure. `--dry-run` is the ONLY path that may exit non-zero (used by spawn-time precheck so callers can refuse cleanly).

agy hooks (all dispatched through `agy-dispatcher.ts`; registered in the workspace `.agents/hooks.json`, NOT via an inline flag):
- `hooks agy-pre-tool-use <agentId>` → `agy-pre-tool-use.ts`: translates the agy tool call (`agy-tools.ts`) to a synthetic Claude call and runs `checkPathAccess`; deny-by-default; logs each denial. Captures `agy_conversation_id` defensively if empty.

- `hooks agy-stop <agentId>` → `agy-stop.ts`: writes `state: "waiting"` / `"complete"` from the transcript tail (last `PLANNER_RESPONSE`); returns `{"decision":"continue"}` on uncommitted work (D9).

Primary-Claude hooks:

## Agent types (`src/agent-types.ts`)

Agent types are `.md` files with YAML frontmatter in `~/.itsybitsy/agent-types/`. The `.md` file on disk is the primary source of truth — `loadAgentType()` reads only from disk and throws if a file is missing. Default types (manager, worker, repo-coordinator) plus three layer files (`_all.md`, `_non_coordinator.md`, `system-coordinator.md`) are embedded in the binary via text imports from `docs/agent-types/*.md` and auto-populated on first run via `ensureAgentTypesDir()`. The two coordinator type names are the only coordinator-specific type names; they live as `REPO_COORDINATOR_TYPE` / `SYSTEM_COORDINATOR_TYPE` (plus `isCoordinatorType()`, which decides who skips `_non_coordinator`) in `src/coordinator-type-names.ts`. A per-repo coordinator is identified by `agentType: "repo-coordinator"` alone; meta.json has no separate coordinator flag. The reserved agent IDs `coordinator`/`system`, the `ib-coordinator` tmux session, and the `@system` / `@<repo>` addresses are separate names and are not in that module.

`AgentType` interface: `name`, `description`, `canSpawnChildren`, `spawnable`, `remoteControl`, `icon`, `model`, `permissions`, `paths`, `toolsIgnoringPaths`, `toolsIgnoringPathsErrors`, `sandbox`, `repos`, `markdownBody`.

- `spawnable` defaults to `true` when absent; `false` marks layer-only files (`_all.md`, `_non_coordinator.md`, `system-coordinator.md`) that cannot be spawned but whose frontmatter and body merge into spawned agents (`_all.md` into every agent, `_non_coordinator.md` into non-coordinators, `system-coordinator.md` into the system coordinator).
- `remoteControl` is valid only in `system-coordinator.md`: `validateAllAgentTypes()` rejects it in any other file, and rejects a non-boolean value there. Like `spawnable` it is leaf-only (`loadAgentType` reads it from the leaf frontmatter and passes it to `buildAgentTypeFromFrontmatter`; it is not in `mergeRawFrontmatters`'s `SCALAR_KEYS`), and only a literal `true` yields `true`. Consumed by `ensureSystemCoordinator()` and the `ib watch` header light (`src/remote-control-light.ts`) (SPEC.md §15).
- `repos` is an optional list constraining which repos a type may be spawned into.
- `allowedPaths` is **retired** (replaced by `paths:`). A type file that still declares it is a hard validation error pointing at the `paths:` block (SPEC-PATH-ALLOWLIST.md §6.11).
- `paths` is the filesystem policy from the top-level `paths:` block (`allowRead`, `allowWrite`, `deny`). The lists union and exact-dedupe across `_all.md` → `_non_coordinator.md` → inherits → leaf. Each entry is an absolute path, a home path (`~`), a relative path (`./x` / `../x`), or a glob. `newAgent` and `refreshAgentSandbox` call `anchorRelativePaths(paths, repoRoot)` to anchor every relative entry at the main repo root **before** canonicalizing, so `meta.paths` holds only absolute paths and the generator/kernel never see a relative entry; `checkPathsRepoContainment` then rejects an allow entry resolving under `<repo>/.itsybitsy/agents` (a dead entry) and warns on one inside the repo root. `validatePathsFrontmatter(..., { allowRelative: true })` accepts the relative forms at type-validation time. `allowWrite` also grants read; exact canonical read/write ties normalize to write. Config denies win at every depth; otherwise the most-specific match across both lists and runtime roots decides. A missing `paths` key defaults all three lists to empty. In a partial object, only omitted lists default empty; populated `allowRead`, `allowWrite`, or `deny` entries remain present and enforced.
- `toolsIgnoringPaths` lists MCP tools whose calls skip the PreToolUse path checks (SPEC-PATH-ALLOWLIST.md "Tools that skip path checks"). Grammar, sanitizing and the matcher live in the import-free `src/tools-ignoring-paths.ts` (`toolsIgnoringPathsEntryError`, `toolsIgnoringPathsValueErrors`, `sanitizeToolsIgnoringPaths`, `unionToolsIgnoringPaths`, `toolIgnoresPaths`, `metaToolsIgnoringPaths`), shared by `validateAllAgentTypes`, `mergeRawFrontmatters` (union across `inherits:`, invalid entries dropped) and the hooks. Dropped entries: `mergeRawFrontmatters` records each one as `<file>.md: toolsIgnoringPaths...` (from `toolsIgnoringPathsValueErrors`, the same wording `validateAllAgentTypes` reports at `ib watch` startup), `loadAgentType` exposes them as `AgentType.toolsIgnoringPathsErrors`, and `newAgent` (step 6.1, beside the permissions merge) passes each one, deduped across `_all`/`_non_coordinator`/the type, to `logWarning`. The warning fires only at spawn: `@system` never goes through `newAgent` and codex re-reads the type files on every call, so an invalid entry added after a spawn is dropped with no warning until the next `ib watch` startup. Like newAgent's other warnings, it lands in a different place for each caller (this is the one place that lists them; SPEC-PATH-ALLOWLIST.md and the agent-types README point here):
  - CLI `ib new-agent`, or `ib resume <coordinator>` (a reset that re-runs `newAgent`): stderr.
  - `ib watch` dashboard spawn or reset (`n`, `R`): `~/.itsybitsy/watch.log`.
  - Brokered (sandboxed) spawn: the broker runs `newAgent` inside the requesting agent's watchdog, whose stderr is appended to `<repo>/.itsybitsy/agents/<requester-id>/watchdog.log` (WATCHDOG LOG in `ib watch`). The broker relays only `result.stderr`, so the warning is not in the requester's command output.
  - `/respawn` on a repo coordinator: lost. `respawnAgent` runs `ib respawn-self` in a detached `ib-respawn-<id>` tmux session with remain-on-exit off, so its stderr disappears when the session exits.

  Where each CLI gets it: `newAgent` freezes the layer union into `meta.toolsIgnoringPaths` for Claude agents only; `hookCheckPathImpl` in `src/hooks/agent-path.ts` reads it from meta, or for `@system` from `buildSystemHookPolicy()` (`paths-table.ts`, which loads `_all` and `system-coordinator` once per call for both the access table and this list); the codex hook takes it live from `loadMergedAgentTypePermissions` (`src/hooks/shared.ts`) beside its allow list; agy needs none. Every handler passes it to `checkPathAccess` as `PathCheckContext.toolsIgnoringPaths`, consulted after the deny/allow gate and the Bash branch.
- `sandbox` accepts boolean shorthand or an object with optional boolean `enabled`, `rawAllow`, and `domains`. Only literal false opts out in metadata readers and displays. Old filesystem keys under `sandbox:` remain validation errors with `paths:` migration guidance.

## Seatbelt sandbox (`src/sandbox.ts`, `src/ib-commands.ts`)

> **Default-enabled contract.** Kernel sandboxing is enabled unless an applicable type explicitly overrides it. Enabled launches require profile/proxy setup and fail closed on errors or unsupported platforms. Disabled launches omit the itsybitsy wrapper/proxy/collector and restore pre-sandbox process behavior. Hooks remain authoritative for every tool approval and prevent native user prompts in both modes.

- `canonicalizePathsConfig()` expands `~` and canonicalizes authored paths/glob prefixes before `AgentMeta.paths` is persisted. Cross-list membership is preserved in meta for display; `readAgentMeta()` coerces and deep-copies all three lists.
- `normalizePathsConfig()` applies the exact canonical read/write tie rule on a copy. `sandboxPathAccessTable()` adds canonical `AGENTDIR`/`WORKTREE`/`GITDIR` write roots plus roots **keyed on `SandboxProfileParams.canSpawnChildren`**: `REPOAGENTS` is a write root for a spawner and a read root otherwise; `PARENTCLAUDE` (`<repo>/.claude`) is a write root only for a spawner, and so is the optional read-only `REPOID` (`<repo>/.itsybitsy/repo-id`, the id `getRepoId` reads; passed by `prepareSandbox` and the hook's `agentPathAccessTable`) (`profileRuntimeAllowRoots`). It also carries `runtimeDenyRoots` — `TMUXSOCK` (`/private/tmp/tmux-<uid>`) for a non-spawner (`profileRuntimeDenyRoots`), emitted in the deny block after the allow table so it carves the tmux socket out of `/private/tmp`. `generateProfile()` and `resolvePathAccess()` consume the same total sort (literal-prefix segment depth, plain before glob, canonical lexical string, read before write). Each read row emits a read allow plus write deny; each write row emits both allows; configured denies plus the tmux deny root remain last (A3).
- `src/sandbox.test.ts` contains a minimal SBPL last-match evaluator used as the generator oracle, 20 seeded order permutations for every required nesting fixture, a live macOS `sandbox-exec` compile/read/write probe (floor rows, root-listing `ls /` vs `ls /Applications`, and the tmux deny for both spawn keyings; opt-in via `IB_LIVE_SANDBOX=1`, with `floorLayout` sharing its rows with a default test that checks each row's decision against the resolver and the evaluator), and a **LIVE `claude` boot gate** (opt-in via `IB_LIVE_BOOT=1`; skipped by default because it runs a real claude that hangs on the kernel-denied network for the 30s run timeout) that proves the tightened `_all.md` floor boots claude without SIGABRT (it hangs to exit 143, the baseline fail-closed proof). The live harness obtains its executable/syscall floor from `docs/agent-types/_all.md` rather than duplicating it in source.
- **Live probes are opt-in per area, as `IB_LIVE_<AREA>=1`, and only test files read those variables.** The default `bun test` has to pass inside a sandbox, so it gets the same behavior from injected fixtures. `IB_LIVE_SANDBOX=1 bun test src/sandbox-detect.test.ts src/sandbox-collector.test.ts src/sandbox.test.ts --test-name-pattern LIVE` covers the real `sandbox_check`, boot identity, process ancestry, nested sandboxes and profile compilation and enforcement. `liveProbes` (`src/sandbox-live-probes.ts`) turns a missing prerequisite into one failing capability row (`CAPABILITY UNAVAILABLE`) and skips the probes, so it cannot be mistaken for a product failure, and it suppresses nothing once the prerequisite holds. It also backs `IB_LIVE_ACK=1` (`src/ib-ack.test.ts`, a compiled `ib` under a manager profile) and `IB_LIVE_BOOT=1` (above). The others gate on their own variable: `IB_LIVE_CALLER=1` (`src/no-worktree-caller.test.ts` and `src/hooks/agent-context.test.ts`, real OS ancestry) and `IB_LIVE_CODEX=1` (`src/hooks/codex-user-prompt-submit.test.ts`, real model turns).
- `mergeSandboxLayerConfigs()` merges the separately typed `PathsConfig` and `SandboxConfig`. Spawn freezes both in meta. Resume regenerates `sandbox.sb` (in the sealed namespace, `sandboxProfilePath()` in `src/sandbox-log-paths.ts`, with a new attribution tag from `newSandboxTag()`) from the frozen `meta.sandbox` + `meta.paths` (never re-merging the agent-type layers for those), and re-derives ONLY the `canSpawnChildren` spawn key via `metaCanSpawnChildren(agent.meta)` — which uses `meta.canSpawnChildren` when present and otherwise reads the type `.md` (`loadAgentType`) for the key. That one type read is deliberate (the type file is read-only to agents, so it is the safer source than freezing the key into agent-writable meta; A4 closes the boundary, SPEC-SANDBOX.md §4C.3). An unchanged agent still replays the same rules (only the tag changes); a `meta.canSpawnChildren` toggle flips exactly the REPOAGENTS op, the PARENTCLAUDE root, and the tmux deny.

Claude alone contributes `PROJECTDIR`/`SCRATCHPAD`; codex and fugu omit those roots. Agy contributes its own `AGYSTATEDIR` (the whole `~/.gemini`, `agyStateDirFor(home)`) as an agy-only write root and omits the Claude roots; like every CLI it is sandbox-wrapped at spawn and resume when enabled (a diagnostic `agy --version` probe may already have run at spawn). The spawn key comes from `initialMetaJson` at spawn and `agent.meta` at resume, so a `meta.canSpawnChildren` toggle flips exactly the REPOAGENTS op, the PARENTCLAUDE root, and the tmux deny between spawn and resume, and an unchanged agent replays the same rules (only the tag changes). - **Sandboxed spawn goes through the watchdog (`src/spawn-broker.ts`).** `prepareSandbox()`'s compile lint (a nested `sandbox-exec`) and proxy-port bind cannot run inside a sandbox, so `ib new-agent` in a sandboxed process (`isSandboxedProcess()`, `src/sandbox-detect.ts`, kernel `sandbox_check` via `bun:ffi`) never reaches `newAgent()`: `routeNewAgentThroughWatchdog` (called from the `new-agent` case in `src/index.ts`, before any repo lookup) queues `<agentDir>/spawn-requests/<id>.json` and waits ≤30 s for `spawn-results/<id>.json`, failing at once when `hasLiveWatchdog` is false. The unsandboxed per-agent watchdog (`runPerAgentWatchdog`, hooks injectable via `setPerAgentSpawnBroker`) runs `processSpawnRequests`: at-most-once, allowlisted fields only, `meta.json` verified against the seal, then `newAgent(..., { _trustedCaller })` — `NewAgentOptions._trustedCaller` replaces the cwd-based caller lookup, which cannot work from the watchdog. Watchdog tests must stub the hooks (like `setPerAgentDrain`) so they never touch the filesystem. Requires the `ib` build flags `--no-compile-autoload-dotenv --no-compile-autoload-bunfig` (AGENTS.md), or a sandboxed `ib` starts with an empty environment.
- **Sandboxed lifecycle commands use the same queue (`src/lifecycle-broker.ts`).** A spawner's profile grants neither the main repo root nor `.itsybitsy/archive`, so a sandboxed `ib retire` / `ib merge` / `ib rehire` cannot run `git -C <main repo>`, archive the agent or read the archive. The `retire`, `merge` and `rehire` cases in `src/index.ts` call `routeLifecycleThroughWatchdog`, which (through `resolveRoutedCaller` in `spawn-broker.ts`, shared with `ib ask`) routes ONLY a worktree agent with its itsybitsy sandbox enabled and returns null (→ direct path, as before) for everyone else: not sandboxed, not an agent, `worktree:false` (its per-agent watchdog exits at once — `runPerAgentWatchdog` stops when `<agentDir>/repo` is missing — and its profile grants the repo root), or `meta.sandbox.enabled === false` (codex then runs in its own sandbox, so `isSandboxedProcess()` is still true, and there is no seal). The request `{v, id, op, target, keep?}` goes into the same `spawn-requests/` directory and `handleOneRequest` in `spawn-broker.ts` hands anything with an `op` field to `handleLifecycleRequest` (except `op: "ask"`, below). Shared pieces live in `spawn-broker.ts`: `submitWatchdogRequest` (write, poll, timeout, withdraw) and `verifyBrokerRequester` (meta + seal). Authorization is `checkManagerCommandAccess(op, target, caller, agentsDir, opts)` in `src/hooks/agent-path.ts` — the body of the hook's `checkIbCommandAccess`, callable without a command line. There null means "allowed" only; a command outside `IB_MANAGER_ONLY_COMMANDS` is denied (so a new op must be added to that set; `lifecycle-broker.test.ts` checks every op in `LIFECYCLE_OPS` against a stranger). The broker trusts no unsealed field of the requester's own `meta.json` (every agent can write its own): it resolves a retire/merge target by its directory entry first (`findAgentInRepo`: `storageDir` must be `agents/<target>` exactly and `meta.id` must agree — `meta.id` is agent-writable and `readAllAgents` reports it as the id), refuses a self-target by id and by resolved directory (a case variant opens the same directory on macOS), passes the seal-verified meta as `opts.callerMeta` so the rule does not re-read the file, sets `opts.ownArchiveOnly` for a rehire, and merges into `<agentDir>/repo` (lstat: a real directory) whatever `meta.worktree` says. A brokered merge passes `MergeAgentOptions._brokeredCaller = { cwd }` (that worktree): inside `mergeAgent` it replaces `process.cwd()` and forces agent (`--ff-only`) semantics, because the watchdog's cwd and tmux environment are not the requester's. A brokered rehire calls `rehireAgent(id, { repoPath })`, which searches only that repo's archive. The hook side has one matching exception: the rule returns no decision for `ib rehire` when `archiveHiddenBySandbox()` is true (sandboxed, and listing `<repo>/.itsybitsy/archive` fails with EPERM/EACCES), because the hook cannot read the archived `meta.json` there; such a caller is either routed to the watchdog, which re-runs the rule unsandboxed, or fails in the same sandbox. Seams are `SpawnServerDeps.lifecycle`.
- **Sandboxed `ib ask` uses the same queue (`src/ask-broker.ts`).** `askQuestion()` writes `<repo>/.itsybitsy/user-questions.json`, and a worktree agent's profile grants `<repo>/.itsybitsy/agents` only. The `ask` case in `src/index.ts` calls `routeAskThroughWatchdog(question, agentId)` before any repo lookup; it routes the same callers as the lifecycle broker (`resolveRoutedCaller`) and returns null (→ direct path, as before) for everyone else. A routed caller is refused when `agentId` (`--id`, or the id from the cwd) is not its own. The request `{v, id, op: "ask", question}` goes into `spawn-requests/`, and `handleOneRequest` in `spawn-broker.ts` hands `op: "ask"` to `handleAskRequest`: strict parse (question text only — no agent, repo, path or harness flag), `verifyBrokerRequester`, then the normal `askQuestion(repoPath, agentId, question)` with the WATCHDOG's agent id, so the top-level rule, the config check, the log line and the `say` / Telegram notifications run unchanged, outside the sandbox. The client runs the top-level rule itself first (`askTopLevelRefusal` in `ib-commands.ts`, the function `askQuestion()` uses), so a sub-agent gets the "use `ib send <manager>`" hint and not a watchdog hint; it then waits `SPAWN_CLIENT_TIMEOUT_MS` (30 s) and maps the two old-watchdog answers (`unsupported field 'op'`, `unsupported field 'question'`) to a restart hint. The session-start hook's harness question (`fromHarness`) is NOT routed: it still calls `askQuestion()` in the sandboxed process. Seam is `SpawnServerDeps.askQuestion`.
- **Sandboxed `ib send` uses the same queue (`src/send-broker.ts`).** The outbox write is allowed under `~/.itsybitsy/agents/`, but target resolution lists every registered repo's `.itsybitsy/agents`, and a worktree agent's profile grants its own repo's only. The resolver (`resolveSendTarget` / `resolveTarget` / `matchAgentById`) lives in `src/resolve-target.ts`, re-exported by `src/index.ts`; `resolveSendTarget` returns the error text, `resolveTarget` prints it; it reads agents with `readAgentsOfRepos` (disk only, no `tmux list-sessions`). Its "Agent not found" errors name any searched repo's agents directory that could not be listed (`unreadableAgentsDirsNote`). The `send` case in `src/index.ts` reads the `-f` file first, reads the message body at most once (`messageBodyReader`: inline > file > stdin), then calls `routeSendThroughWatchdog({ target, fromAgent, readMessage, usage, repos })` before resolving the target. Same callers as the ask broker (`resolveRoutedCaller`); a routed caller is refused when `--from` is another agent, and a send to itself returns null (`targetIsCaller`: the resolver over the caller's own repo only). The client returns null (→ direct path) when the watchdog is not live, when it answers one of the two exact old-watchdog errors (`OLD_WATCHDOG_ANSWERS`), or when the target/message cannot travel in a request; after a current watchdog took the request, a timeout or failure is returned as is (no second send). The request `{v, id, op: "send", target, message}` goes into `spawn-requests/`, and `handleOneRequest` hands `op: "send"` to `handleSendRequest`: strict parse, `verifyBrokerRequester`, `listRepos`, `resolveSendTarget(target, repos, <agentDir>/repo)` (so `@coordinator` is the requester's repo), then `sendMessage` / `teamSend` / `sendToSystemCoordinator` (lazy `import("./index")`, as the watchdog's notifications do) with `{ fromAgent: <watchdog's agent id> }` and never `stageAttachments`. A resolved agent that is the requester is refused, and a team drops it (`isAgentAt`: same id in the same repo, or the same directory via `isSameDirectory`, now shared from `spawn-broker.ts` with the lifecycle broker; `teamSend`'s internal `excludeRecipient`), because the requester writes its own `tmux_session` and heartbeat. `deliverMessage` and `sendMessage` refuse a `tmux_session` that fails `isValidTmuxSession`. Seams are `SpawnServerDeps.send`.
- **Prompt-free tool authorization (clarified contract).** Codex/Fugu always use `-a never`; enabled mode pairs it with `-s danger-full-access` inside Seatbelt, while disabled mode uses no `-s` and selects the inline `itsybitsy_agent` permission profile (formerly `-s workspace-write`). Claude enabled mode adds `--dangerously-skip-permissions`; disabled mode emits neither it nor `--permission-mode`. Claude PreToolUse applies `permissions.deny` before allow and returns an explicit decision before native permission resolution, so neither mode prompts. Disabled mode changes the process boundary, not the hook-authorization contract.
- **Attribution tags (`src/sandbox.ts`).** `generateProfile(config, paths, params, tag)` requires a tag (`SANDBOX_TAG`, `ib-agent:<32 hex>`, from `newSandboxTag()`) and ends every deny with `(with message "<tag>")` through ONE helper, `denyRule`; `tagRawRule` re-emits each top-level `(deny …)` of `rawAllow` through it and refuses a deny it cannot tag (also reported by `validateSandboxFrontmatter`). `sandboxProfileTag()` reads the tag back from the profile's second line (the tagged default deny); `attach` uses it. `prepareSandbox` (`src/ib-commands.ts`) writes the profile to `sandboxProfilePath(agentDir)` = `~/.itsybitsy/sealed/sandbox-logs/<sha256(agentDir)>/sandbox.sb` (0600), never the agent dir, because the tag's nonce must stay secret from other agents. The teardowns that delete the seal (retire, merge, nuke, failed-spawn cleanup) and `resolveOrphanedDir` (`src/health-check.ts`) also call `removeSandboxProfile(agentDir)` (best effort; it also removes the namespace dir if empty). A launch still running at teardown keeps the namespace; its supervisor subshell (`sandboxDenialScriptPreamble`) runs `rmdir` on the namespace after removing its launch dir, which succeeds only once the profile is gone.
- **Kernel-denial collector (`src/sandbox-collector.ts`; ON).** `SANDBOX_DENIAL_COLLECTOR_ENABLED` in `src/sandbox-log-launch.ts` gates it and is `true`; set to false, `sandboxDenialScriptPreamble()` returns `""` and `sandboxDenialExecPrefix()` returns the plain sandbox-exec prefix (both take an `enabled` override for tests). When on, the preamble's supervisor subshell runs `ib sandbox-collector attach` (registrar + per-launch supervisor), and the gate in front of the CLI only closes fd 9 and execs the wrapper. `attach` reads the tag from the launch's sealed profile, holds `sandbox-collector/clients.lock` LOCK_SH for its whole life, writes `registration.json` (protocol 2: agent.log, boot, owner + registrar as PID + birth, token, tag) into the sealed launch directory and an entry into `~/.itsybitsy/sealed/sandbox-collector/inbox/`, and waits for `ready` / `failed`. Whenever it can take `daemon.lock` LOCK_EX|LOCK_NB (no daemon), it has won the role and starts `ib sandbox-collector serve --lock-fd 3` detached, handing over the locked fd (`spawnSandboxCollector`), at most `MAX_STARTS` times. `serve` keeps that fd, runs ONE `ib sandbox-log-stream` helper (argv from `sandboxLogStreamArgv`, `--level default`; the predicate passes only tagged `Sandbox:` reports and its own markers), re-adopts every live launch directory at startup, validates each registration with `validateRegistration` (namespace hash binding, private directory, well-formed tag, same boot, owner and registrar named by PID + birth and alive with that birth, registrar descending from the owner, both unsandboxed via `sandbox_check`; a rejected directory gets `failed` + `done`=`rejected`; a tag another launch holds is rejected too), and maps tag → launch. The stream pump parses each line with `parseSandboxReport` (`src/sandbox-denials.ts`: real kernel report fields only, tag = text after the LAST newline, `N duplicate report(s)` count kept) and appends `formatSandboxRecord` to the launch whose tag equals it exactly; it also writes `ready` when a launch's marker comes back. The loop (`LOOP_MS` = 1000) reads the inbox and control files, checks each launch's stop file, owner and registrar, re-emits markers, and writes the heartbeat. It exits once it has no launch and can take `clients.lock` LOCK_EX, closing `daemon.lock` before `clients.lock`. `restart` (and SIGTERM) leaves without `done` after giving up the role, so attaches start a successor that re-adopts; `stop` finishes every launch; `status` marks a heartbeat older than 5 s STALE (fix: `kill -9 <pid>`). `src/sandbox-processes.ts` now only reads PID/ppid/birth, the boot id and `sandbox_check` for registration checks; nothing samples process trees. Seams: `ServeOptions.lockFd` / `spawnStream` / `emitMarker` / `openProcessReader` / `loopMs`, `AttachOptions.startCollector` / `pollMs` / `openProcessReader`; the tests' fixture process table goes through `openProcessReader`, so they never read the kernel. Design and trust model: `docs/SANDBOX-SHARED-COLLECTOR.md`.
- **`ib watch` Collector light (`src/sandbox-collector-light.ts`).** `sandboxCollectorHealth()` is the in-process twin of `ib sandbox-collector status`: `sandboxCollectorRunning` (LOCK_SH|LOCK_NB on `daemon.lock`), then a `heartbeat.json` read (`updatedAt` age vs the same `STALE_HEARTBEAT_MS` that `status` uses), or, with no daemon, `tryCollectorLock(clientsLock)` (LOCK_EX|LOCK_NB, closed at once) to see attached launches. The header draws it first, before Remote Control and Telegram; `?` help shows `collectorHealthDetail`.
- **Claude `worktree:false` settings isolation.** Per-repository coordinators and regular `--no-worktree` Claude agents receive an agent-local `<agentDir>/.claude/settings.local.json`, passed explicitly via `--settings`; the itsybitsy hook reads that exact file as the agent policy. This separates generated state without changing setting sources: normal user/project settings still load and may impose additional restrictions, preserving pre-sandbox customization, and their files are never rewritten. Spawn, resume, rehire, and sandbox refresh preserve that location and mode split.
- **No-worktree provider gate.** Claude is the only CLI that supports `worktree: false`. New Codex/Fugu/agy agents reject `--no-worktree` before side effects. Resume and rehire reject non-Claude `worktree: false` metadata before generated-file, trusted-workspace, or other shared-state mutation; their hook/rule/precheck implementations require a real worktree and do not have a partial fallback.

## Sealed record (`src/agent-seal.ts`, A4 G3)

Closes the agent-editable-meta boundary of §4C.3: `AGENTDIR` is a kernel write root, so an agent can edit `meta.canSpawnChildren`/`meta.agentType` and try to respawn into a spawner profile. The seal makes that tamper-evident **for non-spawners**.

- **`src/agent-seal.ts`** is pure/IO helpers: `computeSealInputs(meta)` → `{agentType, canSpawnChildren (via metaCanSpawnChildren), paths, sandbox}`; `computeSealRecord()` adds a sha256 over the canonical (key-sorted) inputs JSON; `writeSealRecordDirect`/`readSealRecord`/`deleteSealRecord`/`verifyMetaAgainstSeal`. `sealPath()` = `<home>/.itsybitsy/sealed/<repoId>-<agentId>.json`; home defaults to `process.env.HOME ?? homedir()` (the `~/.itsybitsy` convention, so a HOME override isolates it in tests). `_all.md` `paths.deny` lists `~/.itsybitsy/sealed`. Shared seal/capability path constructors and capability issuance validate the eight-hex repository ID and established agent-ID syntax before filesystem access, preventing path traversal.
- **`ib-commands.ts` orchestration.** `sealAgentRecord(repoPath, id, meta, helperCwd)` tries a direct write. `deleteAgentSealChecked()` performs checked deletion, including expected-record matching when supplied. On `EPERM`/`EACCES`, seal writes, deletion, and resume verification use `runHelperViaTmuxServerBlocking` (`tmux run-shell` without `-b`). The trusted helper creates a short-lived, owner-only, one-use capability in the sealed tree, bound to the action, repository, agent, and normalized intent. It invokes internal `ib sandbox seal <id> --repo-id <repoId>`, `ib sandbox delete-seal <id> --repo-id <repoId>`, or `ib sandbox verify-seal <id> --repo-id <repoId>` with the capability token; agent hooks deny these internal commands. The privileged handler verifies the exact write/delete postcondition or performs strict read-only seal verification. The parent requires an explicit exit-status result, plus validated JSON output for verification, in a unique `.ib-seal-helper-*` directory directly under root-owned `/private/tmp`. The trusted helper exclusively creates this directory, atomically publishes output before status, and performs exact cleanup after the parent reads the result; the parent only reads and checks that cleanup removed it. Enabled profiles deny both `file-write*` and the separate `file-link` operation on the reserved basename and subtree while allowing reads. Shared hook policy also treats link creation from a protected source as a mutation. The stable parent directory prevents substitution through a renamed agent directory; it neither trusts the tmux client exit status alone nor reopens the denied sealed tree. Enabled spawn and rehire seal before launch; refresh updates the seal transactionally with metadata. Disabled spawn/rehire clear stale seals. Failure cleanup and retire/nuke/merge use checked deletion with the authenticated fallback before discarding metadata needed for recovery.
- **Verification.** `resumeAgent` (covering `respawnSelf` and rehire) verifies frozen metadata before proxy or metadata mutation. It uses a strict reader; permission errors trigger an authenticated, one-use `verify` capability through the trusted helper, never an inference that the seal is absent. Enabled resume refuses a missing seal; either mode refuses an existing mismatched seal, including a metadata-only toggle to false. Legitimate disabled metadata may resume when the seal is truly absent. Corrupt records, helper failures, missing completion, and invalid verification output fail closed. Operator-only refresh takes one strict seal snapshot before pausing or changing policy; unreadable/corrupt seals cause an early refusal. A valid existing seal must match current metadata; a truly missing seal remains recoverable by refresh. Rollback restores the snapshot or leaves an explicit retryable failure. Residual: a spawner still reaches the seal dir via its tmux socket (accepted).

## Telegram channel subsystem (`src/channels/`)

The Telegram bridge lives entirely here (NOT in the sibling bash `ittybitty`). Hand-rolled Bot API client — no grammy. Boot (`boot.ts`) runs at `ib watch` start: probe → resolve private chat id → construct `TelegramDispatcher` (inbound long-poll) + `TelegramOutbox` (outbound queue).

- **Boot retry** (`RetryingProber` in boot.ts): both boot probes retry a TRANSIENT failure — fetch throw/timeout, status 0, 429, 5xx (`isTransientStatus`), or a 2xx without an `ok:true` envelope (body truncated or reset: `HTTP 200 (bad body)`) — with `backoffDelayMs` 1 s → 60 s cap, jittered; a 429 waits `max(Retry-After, backoff)` (`probeOnce` now returns `retryAfterSec`). It retries until success or `BootOptions.signal` fires (→ `reason: "aborted"`; ib watch aborts on quit). One prober serves both probes, so log dedup and backoff carry from step 1 to step 2; each success ends the streak. watch.log gets `Telegram connect failed (<label>); retrying with backoff` once per error class per streak and `Telegram connected after Ns` on recovery; `onRetry({reason, attempt, delayMs})` feeds the dashboard. A wake (`BootOptions.wake`) aborts the per-attempt controller: an in-flight probe or backoff wait ends, the attempt count resets, no failure is counted. Permanent outcomes and their messages are unchanged (no-token, 401/403 `probe-auth`, 409, other 4xx `probe-other`, allowlist write failure `probe-other`, no-allowlisted-inbound, ambiguous-first-use); `probe-network` is gone. Labels are `classifyError()` output (timer-fired aborts → `errno:ETIMEDOUT`, as in `getUpdates`), never `err.message`. `probeOnce` throws its signal's abort reason when the body could not be read AND the signal fired (timer, stop or wake mid-body), so a timeout mid-body is `errno:ETIMEDOUT` and a wake mid-body takes the wake path; the dispatcher's startup probe catches that throw like any network failure. Why: 2026-11-20 an `ib watch` started during a 502 run logged `probe failed (The operation timed out.)` and ran a whole session with no dispatcher and no outbox.
- **Poll loop resilience** (dispatcher.ts): `runLoop` returns only after `stop()`. Each iteration gets an `AbortController` composed with the stop signal (`AbortSignal.any`); `reconnectNow(reason)` aborts it, so the in-flight poll or backoff wait ends and the next poll starts at once with a fresh backoff (the client's backoff is per `getUpdates` call, so a new call resets it too). A non-abort throw from `getUpdates` (the client retries every transient failure itself, so this is a bug or a non-array `result`) is fed to the health machine as a retry and backs off 1 s → 30 s via `pause()` instead of the old immediate `continue`. `superviseLoop` wraps `runLoop`: if the loop's own error handling throws (e.g. a throwing log sink) it logs `poll loop crashed (...); restarting` and restarts after a backoff; it never rejects, so `loopDone` has no catch. `DispatcherHealth.reasonAt` = when the current failure label first appeared (`setFailureReason`). `DispatcherOptions.pollTimeoutSec` sets the long-poll seconds (tests use 0).
- **Wake detector** (`wake-detector.ts`): a 5 s interval (unref'd) compares `Date.now()` between ticks; a gap > interval + 15 s means the machine slept (timers stall during macOS sleep, the wall clock does not) and fires `onWake({sleptMs})`. Clock and timer are injectable. A clock jump or a long event-loop stall also fires; that only costs a needless reconnect. Created in `launchDashboard` only with a token, stopped on quit.
- **Connection state** (`connection-view.ts` pure, `connection-monitor.ts` stateful): `deriveTelegramConnection` maps boot progress + `dispatcher.getHealth()` + `outbox.getHealth()` to `connecting` (boot retrying, or dispatcher `start()` not settled) / `connected` (polling, outbox not stalled) / `reconnecting` (dispatcher retrying, or outbox stalled) / `disabled` (boot ok:false, or `down` after `start()` settled — a startup 409). `TelegramConnectionMonitor` is created in `launchDashboard` before the boot: `bootRetry`/`bootDisabled` from the boot, then `attach(dispatcher, outbox)` before either starts and `dispatcherStartSettled()` when `start()` settles. On each change (`sameTelegramConnection` decides) it calls `onChange` (→ `DashboardComponent.setTelegramConnection`, only with a token) and writes `~/.itsybitsy/channels/telegram/status.json` (`writeTelegramStatus`, always — a no-token ib watch reads as disabled, not "not running") through ONE promise chain, so writes never interleave. It also owns the watch.log lines `telegram: disconnected (<reason>)` / `telegram: reconnected after Ns` (moved from the dashboard, text unchanged), calls `outbox.kick()` on retrying → polling, and on a wake logs `telegram: wake from sleep detected (slept ~Ns); reconnecting`, calls `dispatcher.reconnectNow("wake from sleep")` and `outbox.kick()` (while boot is retrying it only logs; boot hears the wake itself). The 5 s `telegramStatusTimer` is just `monitor.refresh()`, a backstop for changes that fired no event. `outboxPending`: while there is no outbox (boot connecting, or disabled) each refresh counts the item files in the outbox dir (`countQueuedOutboxItems`, one readdir; seam `ConnectionMonitorOptions.countQueuedItems`), so a startup outage still shows `connecting — HTTP 502 (40s ago); 2 queued`; once attached, `outbox.getHealth().pending` is used. Writes stay edge-triggered (a count change is a view change). Quit order: abort the boot, stop the wake detector, `monitor.dispose()` (unsubscribe, stop publishing, await queued writes, `clearTelegramStatus()`), THEN stop dispatcher/outbox — so the stop's `→ down` is neither logged nor written as disabled. Outbox contract it relies on (see **Outbox**): `onHealthChange` fires only when `pending`/`stalled`/`lastError` change; `lastError` is set only while stalled; `kick()` is safe to call any time (a no-op unless the head is stalled and waiting, or inside a 429's `retry_after`), so the monitor calls it unconditionally on recovery and wake. The outbox refreshes `lastErrorAt` on every stall retry WITHOUT an event, so `outboxHealth()` pins it to when the current label first appeared; otherwise every 5 s backstop `refresh()` during a stall would publish and write a new view, and the help age would restart at each retry. The real stall → recovery-kick path is pinned in `connection-monitor.test.ts` against a real `TelegramOutbox`.
- **Header light + help row**: `telegramLight(view)` — green connected, yellow connecting/reconnecting (outbox stalled included), red disabled; `setTelegramConnection` keeps the view and renders only on a light change. `?` help shows `telegramHelpDetail(view, now)` as the last Status row (after Remote Control), only with a token: `connected`, `connected; 2 queued`, `connecting — errno:ETIMEDOUT (12s ago)`, `reconnecting — HTTP 502 (40s ago); 2 queued`, `disabled — bot token rejected (HTTP 401)`; word-wrapped to 48 columns onto rows with an empty key. A disabled reason is `BootDisabled.message` minus `Telegram routing disabled: ` (`disabledReason`).
- **Fake-server test** (`telegram-reconnect.test.ts`): real client + real dispatcher against `Bun.serve({ port: 0 })`; faults = 5xx burst, 429 + Retry-After, a poll that never answers, a body truncated by a lying Content-Length, a poll stranded until `reconnectNow`. Each checks exactly-once delivery and the offset advance. Recipe for a new fault: push it onto `fake.faults`.

- **Inbound**: `dispatcher.ts` long-polls `getUpdates` with `allowed_updates: ["message", "message_reaction"]`, allowlist-filters, coalesces per-chat text into a `<channel source="telegram">` block, and delivers to the system coordinator via `sendToSystemCoordinator(..., {fromAgent: "@telegram"})`. `normalize()` → `NormalizedMessage` (now carries `messageId`). `wrapChannelReminder` surfaces `message_id` (single) / `last_message_id` (burst).
- **Reactions (inbound)**: `message_reaction` updates → `normalizeReaction()` (same allowlist, diffs `old_reaction`/`new_reaction`) → `wrapReactionReminder` → delivered as a distinct `kind="reaction"` event. Not coalesced with text; never enters the offline y/n flow (informational — dropped if coordinator offline).
- **Reaction context** (`message-cache.ts` + `formatSendOk` in outbox.ts): a reaction block carries a TEXT PREVIEW of the reacted-to message plus whose it was — `Reacted 👍 to message 1584 (your message): "..."`. Two halves. (1) `ib tgsend` now echoes the sent id: `ok (message_id 1584)` / `ok (3 parts, message_ids ...)`, degrading to the old bare `ok` / `ok (N parts)` when no id is determinable and to a `queued: ...` message when it has not gone out yet — this is the DURABLE half (id lands in the coordinator's own history, survives restart). `processText` collects `resp.result.message_id` per chunk INCLUDING on a retried attempt, and keeps the ids in `<base>.progress` so a resumed send still lists all of them. (2) `message-cache.ts` is a module-level, **memory-only**, 200-record oldest-first ring (text capped at 300 CODE POINTS) shared by dispatcher + outbox — same process, same chat id, so no boot plumbing. Seeded per-chunk on send and per-message on `deliver()` (every message in a coalesced batch). **Never persisted — do not add disk backing.** `deliverReaction()` does the lookup; `wrapReactionReminder(reaction, preview?)` stays sync/pure. A cache MISS (restart, eviction, pre-feature message) must render the id-only form: the summary line + `<channel>` body are byte-identical to pre-feature output, the trailing reply hint is not. The echoed-id sentence rides ONLY on reaction blocks (`REACTION_REPLY_HINT` = `REPLY_HINT` + one sentence, derived so they can't drift) — ordinary message blocks keep the unchanged `REPLY_HINT`, since a per-message sentence is permanent context tax for a rare case, and `ib tgsend` prints the id regardless. `dispatcher.test.ts` + `reaction-context.test.ts` pin that behavior, but they compare the current code against ITSELF — the pre/post equivalence was established by review, not by the suite. `ib tgsendfile` does NOT echo/cache (bare `ok`). **`truncateCodePoints` is load-bearing twice over and easy to break "safely":** `.slice` returns a VIEW retaining the parent (200 records × 300 chars out of 1 MB parents pinned ~103 MB; `sendChunks` slices chunks out of the uncapped full `tgsend` payload), and cutting on code units severs surrogate pairs. `Array.from(s.slice(0,MAX)).join("")` fixes NEITHER — the pair is already severed; the pre-slice must be `MAX*2` units, THEN `MAX` code points, then `join`. Guard and cut must both count code points, and the helper is applied at BOTH the storage and display caps (the display cap can't cover for the storage one — `formatMessagePreview` shrinks before it measures).
- **Reply context** (`extractReplyContext` in dispatcher.ts): a swipe-reply gets an `in_reply_to="1584"` attribute plus a leading `Replying to (your message): "…"` body line. **Structurally different from reaction context and easy to conflate:** Telegram embeds the FULL replied-to Message (text and all) in `reply_to_message`, so this path reads the text straight off the update — no cache, durable across an `ib watch` restart, works for a message months old. The cache is only a LAST resort (reply to a bare photo/sticker: text → caption → `lookupMessage` → id-only form) and is probed at most once. Direction comes from `reply_to_message.from.is_bot` (the coordinator sends through the bot), else the cache's direction, else the whose-clause is OMITTED — never guessed, since a confident wrong attribution reads as fact. **An ordinary message must gain NOTHING** (Adam's constraint): `replyTo` is undefined for non-replies and every addition is gated on it, so those blocks stay byte-identical — pinned against whole-block literals in `dispatcher.test.ts`. The COALESCED branch has one header for N messages, so there's no per-message attribute slot: the reply line sits directly above its own body and carries the id INLINE (`Replying to message 1584 (your message): "…"`), which is why the body line differs between the single and coalesced branches on purpose. `formatMessagePreview` is shared with the reaction path (one truncation site). NOT verified against real Telegram — the three live-API assumptions (a real swipe-reply populates `reply_to_message`; `from.is_bot` is true on the bot's own messages; a media reply carries `caption`) are hand-built fixtures in the suite; see the §4.10 sanity-check step.
- **Reactions (outbound)**: `ib tgreact <emoji> [--message-id <id>] [--clear]` → `telegramReact()` (ib-commands.ts) validates the emoji (`reactions.ts`, Telegram's documented set), drops a `<stem>.react.json` `{message_id, emoji}` descriptor into the outbox, waits ≤3s for the result. `TelegramOutbox.processReaction` → `client.setMessageReaction` (transient retry and stall as for texts, see **Outbox**). Default target = the last-message cache.
- **Last-message cache** (`last-message-cache.ts`, modeled on `chat-id-cache.ts`): `deliver()` persists the newest inbound `{chat_id, message_id}` to `~/.itsybitsy/channels/telegram/last-message.json` so the separate `ib tgreact` process can react to "the latest message".
- **Attachments (inbound)**: a message carrying a photo/document/voice/audio/video/video_note/sticker is DOWNLOADED. `describeAttachment()` (dispatcher.ts) extracts a descriptor (kind, file_id — largest PhotoSize for photos — advertised size, sanitized display name); `resolveAttachment()` runs in `processBatch` before grouping: 20 MB pre-guard → `client.getFile(file_id)` → `client.downloadFile(file_path)` (re-guards 20 MB on the wire) → `storeInboundFile()` writes to `~/.itsybitsy/channels/telegram/inbound/<chat>/<unix-ms>-<safeName>` and the body becomes `[user sent photo: /abs/path (123 KB)]` (caption prepended). Too-big / failed downloads surface a clear coordinator note (and a Telegram reply for too-big) instead of a path. The old "Received attachment — text only supported" reply is GONE. Attachment types live in `types.ts` (PhotoSize/Document/Voice/Audio/Video/VideoNote/Sticker/TelegramFile).
- **Inbound store** (`inbound-store.ts`, dir-override like outbox): downloaded files kept INDEFINITELY by default (the agent may still need them); `pruneInboundOlderThan(ttl, now)` is opt-in housekeeping (suggested `INBOUND_DEFAULT_TTL_MS` = 30d), not called on the hot path. `storeInboundFile` applies a final path-traversal guard regardless of caller.
- **Attachments (outbound)**: `ib tgsendfile <path> [caption] [--photo|--document]` (default DOCUMENT to preserve bytes; sendPhoto recompresses) → `telegramSendFile()` (ib-commands.ts) drops a `<stem>.file.json` `{path, caption?, kind}` descriptor; `TelegramOutbox.processFile` validates the path (exists/regular/readable/size: ~10MB photo, ~50MB document) then calls `client.sendPhoto`/`client.sendDocument` (multipart via Bun FormData + `Bun.file`; transient retry and stall as for texts, see **Outbox**). The validation reruns on every retry, so a file deleted during a stall fails permanently.
- **Outbox** (`outbox.ts`): file-drop queue under `~/.itsybitsy/channels/telegram/outbox/`. Queue unit is the full dropped filename (`<stem>.txt` text, `<stem>.react.json` reaction, or `<stem>.file.json` file); sidecars are `<base>.result`, `<base>.progress` and `.tmp`. ONE drain loop (`drainLoop`) sends the head of a filename-sorted `queue`, strict FIFO across all three kinds; fs.watch + 0.5s safety rescan feed it, `known` (every item until its files are unlinked) stops double-enqueue. **Transient vs permanent**: transient = fetch throw, status 0, 429, 5xx (`isTransientStatus`); permanent = other 4xx and local validation (empty text, bad descriptor, file missing/unreadable/too large) → `{ok:false}` result + 5s cleanup, as before. Reading the item file: only ENOENT drops it (vanished); any other read error (EMFILE, EACCES, EIO) holds it like a transient failure (label `outbox read failed (<code>)`) and never unlinks it. The same rule covers a text's `.progress`: ENOENT = no progress, any other read error holds the item (sending from part 1 would resend delivered chunks); an unparsable `.progress` is logged and the text is sent from part 1. **Uploads that cannot finish**: a `sendPhoto`/`sendDocument` whose `INLINE_ATTEMPTS` attempts ALL time out (`sendFileMs`, client `timedOut`) fails permanently with `sendDocument timed out 3 times (upload too slow?); not retrying`, so a file too big for the link cannot hold the queue forever (each retry re-uploads all of it); a mix of timeouts and other transient failures still stalls. **Inline retry** (`callWithRetry`): `INLINE_ATTEMPTS` = 3 per API call, `backoffDelayMs` ~1s/~2s (cap 8s) via `sleepCtx`, at least `retry_after` on a 429; a `retry_after` above the 8s cap skips the inline wait and stalls at once (the stall timer honors it and is cancellable). **Stall + hold**: exhausted → the item STAYS ON DISK (no failed result), `getHealth().stalled` + `lastError` (short label: `HTTP 502`, `errno:ETIMEDOUT`) + `lastErrorAt`; nothing behind the head is sent; the head is retried forever (`STALL_BACKOFF` 2s doubling to 60s, jitter, real timer; `OutboxOptions.stallBackoff` for tests) or at once on `kick()` (no-op unless stalled and waiting, or inside a 429's `retry_after`). One `send stalled (...)` line per streak; the first Telegram ANSWER (2xx or permanent 4xx) clears the stall with one `send recovered after N stalled retries` line. A stalled head that leaves the queue WITHOUT an answer (its file vanished, revalidation failed, every upload attempt timed out) also clears it (`endStallWithoutAnswer`: one `stalled item <base> left the queue without a Telegram answer; clearing the stall` line, a health event, `stallStreak`/`retryNotBefore` reset), so the light does not stay yellow with nothing queued. Inline retries log only while not stalled. **Health**: `pending` = queued items not yet delivered incl. the head (items in 5s retention don't count); `onHealthChange` fires only when pending/stalled/lastError change. **Progress sidecar**: a text writes `<base>.progress` `{sent, message_ids}` atomically after EVERY delivered chunk; a retry or a new `TelegramOutbox` after restart resumes at chunk `sent+1` (logs `resuming <base> at part N of M`) and the final `formatSendOk` lists all ids. Deleted with the item. **No resend after finish**: `finish()` writes the final result and unlinks the item and its `.progress` AT ONCE; only the `.result` is kept for the 5s retention (`known` keeps the name until then). So after a crash or restart a reaction or file is resent only if the process died between Telegram's answer and the result write (a text: between a chunk's answer and its `.progress` write). The startup sweep unlinks an item whose `.result` is FINAL (a crash between the result write and the unlink, logged `... already finished before the restart; not sending it again`), then drops `.tmp`/`.result` and ORPHAN `.progress` files. **Cleanup race** (the old `failed to read <stem>.txt: ENOENT` 5s after an ok send, or a double send if the read won): `cleanupItem` unlinks item → `.progress` → `.result` THEN forgets it, and rescans are serialized with forgets deferred to the end of a running rescan (`forgetAfterRescan`). **Interim result**: the head's first transient failure writes `{ok:true, queued:true, message:"queued: ..."}` (`queuedTelegramUnreachable`); only a final result schedules cleanup; clients poll past it. **Duplicate caveat**: a timeout AFTER Telegram accepted the request still retries and `sendMessage` has no idempotency key, so that case can deliver twice — accepted over loss, pinned in `outbox-fake-telegram.test.ts`. `stop()` ends any retry wait, cleans up finished items BEFORE awaiting the in-flight request (which can outlast the dashboard's 2s race) and again after, and leaves unfinished items on disk. **Clients**: `ib tgsend`/`ib tgreact`/`ib tgsendfile` (telegramSend/telegramReact/telegramSendFile → shared `dropInTelegramOutbox` in ib-commands.ts) wait `TELEGRAM_RESULT_WAIT_MS` = 3s (`telegramResultWaitCtx`; covers pick-up + round trip + one inline retry of a FAST failure such as a refused connection or a 502 — a request that hangs times out only after `sendMessageMs`, 15s). Final result → printed as is; interim only → its `queued:` text; nothing → `describeQueuedTelegramItem()` from `readTelegramStatus()`: not running (no file / dead pid), still connecting, reconnecting (`queuedTelegramUnreachable(lastError)`), disabled (reason), or connected but not yet confirmed (makes no claim about earlier messages: the item itself may be the one in flight). Every `queued:` outcome is ok:true / exit 0. Only `@system` may run them from an agent session: `checkIbCommandAccess` (`src/hooks/agent-path.ts`) denies them to every other agent (SPEC §12.1.3).
- **Outbound client calls** (telegram-client.ts): `sendMessage` / `setMessageReaction` / `sendPhoto` / `sendDocument` pass `OUTBOUND_FETCH_INIT` (`keepalive: false`), so every call opens a fresh connection. Root cause of the watch.log `errno:23` sends (2026-11-20, each after ~2 min idle): the send reused a pooled keep-alive socket that had died silently while idle, hung for the full `sendMessageMs` (15 s) and timed out — Bun's timeout DOMException carries `code` 23, and `classifyError` checked `code` before `name`. It now maps `TimeoutError` → `errno:ETIMEDOUT` and `AbortError` → `AbortError` before `code`. Verified on Bun 1.3.10 that `keepalive: false` is honoured (new connection per request, a pooled one is never reused); pinned in `telegram-client.test.ts` by a raw server that answers once per connection and then goes silent (a default fetch's second request times out; the client's sends both land). `getUpdates` / `probeOnce` / `getFile` / `sendChatAction` keep the default. A 2xx whose body cannot be read (truncated, reset, timer fired mid-body) is a SUCCESS with no message id (`accepted()`; Telegram answers 2xx only with `ok:true`), logged once as `HTTP 200 with an unreadable body; treating it as delivered`; a readable `ok:false` envelope stays a failure. These four methods log only PERMANENT statuses (`telegram <method>: status=<n>`) — transient ones are the outbox's to log (one `send stalled` line per streak), and the dispatcher's `replyOnTelegram` logs its own non-ok answers. `sendPhoto`/`sendDocument` fold a fetch throw into status 0 and set `timedOut` when it was the `sendFileMs` timer.
- **Token safety**: the bot-token URL must never be logged — this includes the DOWNLOAD URL (`/file/bot<token>/...` in `downloadFile`) and multipart upload URLs. `classifyError()` (telegram-client.ts) exists for this; all new code reuses it (download/upload failures surface only a status or classifyError label, never `err.message`). Its free-text fallback (`Error:<first 40 chars>`) redacts URLs (`<url>`) and `bot<token>` words (`bot<redacted>`) first, since labels reach status.json, the `?` row and `ib tgsend` output.

- **`pairing.ts`**: the pair protocol (ALPN `itsybitsy/pair/1`, one JSON message per bi stream, `readToEnd(4096)`) as two state machines over the `PairConnection` seam. `PairInitiator` (A: `start` dials + `pair-hello`, `submitCode`) and `PairResponder` (B, run by `respondToPairing`, which reads `pair-hello` and calls the host's synchronous `admit` so the busy check and the claim cannot interleave). `respondToPairing` closes a connection with no `pair-hello` after `HELLO_TIMEOUT_MS` (10 s), and closes on any failed hello read, both with the error code. Both expose `stage` (`connecting` / `code-entry` / `verifying` / `incoming` / `code-shown` / `naming` / `done` / `failed`), `isPending()` (true until done/failed — the busy rule), `cancel()`, `submitName()`. B always sends the last message and then waits (`lingerThenClose`, 5 s cap) for A to close, so a close never races the reply; closes carry `PAIR_CLOSE` codes (done 0, cancelled 1, expired 2, error 3) that `failureFromClose` maps on the other side. Each side sets its final stage BEFORE the close it expects, and the `ended` flag keeps a close this side caused or expected from reading as a failure. `committed` (A got `pair-ok`, B accepted the code) makes `cancel()` a no-op. Timers and the clock are injected; `test-pair-transport.ts` is the in-memory link and fake clock the tests use.
- **`service.ts`**: `PeerService`, what `ib watch` runs (created in `launchDashboard` with a snapshot callback over `dashboard.repos` and `watcher.lastDetectedAgents`, then `dashboard.setPeerService`). An accept-loop failure equal to `quietFailure` (`quietFailureRepeats`) leaves out `closing the endpoint` and (through `closeEndpoint(false)`) `endpoint closed`; while `quietFailure` is an accept-loop failure (`quietBindCycle`, by its `ACCEPT_LOOP_STOPPED` prefix) a bind leaves out `endpoint bound as`, so a flapping endpoint at the cap logs nothing per cycle. A bind after a quiet bind-stage failure (identity, lock, bind) is a change and is logged. `resetRetries()` clears `failures` and `quietFailure` on recovery and on giving up, so the next failure is logged even if it matches the old quiet one. `retryLater` arms nothing when `dialogOpen` is false and the cached `peers` is empty (it logs `<failure>; not retrying: …` and calls `resetRetries()`, a give-up); the timer's bind re-reads `peers.json` first (`whyNotNeeded`, skipped while Peers is visible) and gives up (`stopRetrying`, which also resets `failures`) when nothing needs the endpoint. `cancelRetry()` (from `startBind`, the timer itself, `shutdown`) clears the timer, the countdown and `retryAt`. Do not "fix" this with a Worker (decided in Phase 2 review). Never imports `iroh.ts`; `peer-command.test.ts` makes the addon loader throw to prove it. `checkIbCommandAccess` denies `ib peer` to every agent including `@system` (SPEC §12.1.3), and `_all.md` denies `secret.key`.

## ib-commands (`src/ib-commands.ts`)

All mutations are native (no more `runIb()` / `IbRunner`). `hooksStatus`, `installSafetyHooks`, `uninstallSafetyHooks`, `installInterceptHook`, `uninstallInterceptHook`, `interceptHooksStatus` read/write `~/.claude/settings.json` directly.

Commands: `retireAgent`, `rehireAgent`, `nukeAgent`, `nukeAllAgents`, `pauseAgent`, `resumeAgent`, `reassignAgent`, `mergeCheckAgent`, `mergeAgent`, `sendMessage`, `newAgent`, `diffAgent`, `statusAgent`, `acknowledgeQuestion`.

- Git operations target the agent's repo via `git -C <repoPath>` rather than process-wide `cwd`. Tests inject fake spawn runners via per-command `SpawnContext` instances.
- `mergeAgent(agent, targetDir, { keep })` — `ib merge <id> --keep` (SPEC §3.6). Runs steps 1-10 of the closing merge unchanged (every preflight check, the pre-rebase conflict check, the in-worktree rebase, the caller-dependent `--ff-only`/`--no-ff` merge), then returns before step 11 — no teardown, no archive, no team prune. Same `merging` op marker as the closing merge. CLI flag parsing lives in `parseMergeArgs` (`src/index.ts`); the dashboard `m` dialog exposes the same option through its unchecked-by-default “Keep agent after merge” checkbox.
- Pull before merge (SPEC §3.4 step 0): `pullBeforeMerge` runs between the preflight and the conflict check, for a `main`/`master` target that is checked out in `targetDir`. It calls `pullBranchFromRemotes`, the body of `pullRepo` (`ib pull`), through `mergeSpawnCtx`, so merge tests that mock that context also mock the pull; a mock that answers `git remote -v` with nothing means "no remotes" and the pull is skipped. Remotes come from `listRemotes` (shared with `ib push`/`ib pull`), which counts only remotes with a URL. A sandboxed caller (`isSandboxedProcess()`, in practice a per-repo coordinator) skips the pull with a note in the result; tests pin it with `setSandboxedProcessOverride`.
- `newAgent()` calls `ensureAgentTypesDir()` then validates `--type` exists on disk, rejects layer-only types (`spawnable: false`), and stores `agentType` + `agentIcon` in meta.json. Permission lookup: every agent merges `_all.md` `permissions.allow/deny`; non-coordinators additionally merge `_non_coordinator.md`; all merge their type file's own lists. Deduped before writing `settings.local.json`.
- Every Claude `settings.local.json` written here carries `disableRemoteControl: true`: `buildAgentSettings()` (worktree and `--no-worktree` agents; set after the project `settings.json` spread so a project cannot re-enable it), the per-repo coordinator file in `newAgent()`'s `coordinatorMode` branch, and the `repo-coordinator` branch of `ensureIsolatedClaudeSettings()`. Only the system coordinator can run Remote Control: `ensureSystemCoordinator()` in `src/coordinator.ts` reads `remoteControl` from the `system-coordinator` layer, passes it to `writeCoordinatorFiles()` (which omits `disableRemoteControl` when it is `true`), and adds `--remote-control` with the shell-quoted `coordinator.remoteControlName` config value (falling back to `COORDINATOR_REMOTE_CONTROL_NAME` when empty) to both the fresh and the `--resume` launch lines (SPEC.md §15.3.2).
- `newAgent()` runs `checkSpawnerWorktreeClean(spawnerCwd)` right after prompt validation and before any side effects (SPEC §1.1 step 1a). Drains `git status --porcelain` directly (NOT via `SpawnContext.run`, which would `.trim()` and strip the porcelain XY column's leading space); both streams are drained concurrently via `Promise.all` to avoid pipe-buffer deadlock on large stderr. Skipped silently when `git rev-parse --is-inside-work-tree` doesn't return `true` (non-git cwd: system coordinator home, raw temp dir). The intercept-task hook forwards Claude's reported `input.cwd` as `_cwd` so the check inspects the spawning agent's worktree, not the hook process's own cwd.
- `newAgent()` branches on `parseModel(model).cli`. **Codex path**: skips `.claude/settings.local.json` entirely, writes the worktree `.gitignore` entry, runs the spawn-time dispatcher precheck (`ib hooks codex-pre-tool-use --dry-run <agentId>` + SessionStart + Stop), then generates a codex-shaped `start.sh`. The role text comes from the SessionStart hook, not from `start.sh`. **Claude path**: unchanged — byte-snapshot-guarded at `tests/fixtures/claude-start-sh-baseline.sh`. Coordinators cannot currently be spawned under codex (`--coordinator` + `codex:<model>` is rejected).
- `resumeAgent()` branches on `parseModel(meta.model).cli`. **Codex path**: validates `meta.codex_session_id` present, runs the same precheck, generates codex-shaped `resume.sh` invoking `codex resume "<UUID>"`. **Claude path**: byte-snapshot-guarded at `tests/fixtures/claude-resume-sh-baseline.sh`.
- **agy path** (both `newAgent()` and `resumeAgent()`): skips `.claude/settings.local.json`; refuses a tracked boundary file (D7); writes `.agents/hooks.json` + `.agents/rules/itsybitsy-agent.md` + gitignore; `ensureAgyTrustedWorkspace(realpath(worktree))` BEFORE tmux (D5); runs the `agy-* --dry-run` precheck; stamps `meta.agy_version` (best-effort, timeout-guarded). Resume requires `meta.agy_conversation_id`, regenerates the worktree files, re-trusts, re-prechecks, and re-passes `--model` + effort. `--coordinator` + `agy:` is rejected. Teardown calls `untrustAgyWorkspaceForTeardown` best-effort.
- `ib write-pid <agent-id> <pid>` (`src/index.ts`) routes through `mutateAgentMeta()` in `src/agents.ts` so concurrent meta.json writers can't clobber each other. Used by both claude AND codex `start.sh` + `resume.sh`.

## Agent lifecycle (`src/agent-lifecycle.ts`)

Shared helpers used by multiple ib commands. Mirrors the bash ib teardown / archive / kill / utility functions. All subprocess calls go through `spawnCtx` (a `SpawnContext` from `types.ts`); tests inject a fake runner with `spawnCtx.set(fn)` and reset it with `spawnCtx.reset()`.

The sandbox proxy (`formatAgentDenial`) and the denial collector (`collectorLine`, `formatSandboxRecord`) use the same helper, and the shell writers (start.sh/resume.sh `log()`, the collector preamble in `src/sandbox-log-launch.ts`) use the same `date '+%Y-%m-%d %H:%M:%S'`, so every agent.log line has one stamp. `parseDenials()` still reads the zoned and UTC ISO stamps of older `[Sandbox*]` lines.

Explicit retirement first creates a versioned recovery payload: a hidden Git
ref retains HEAD, `worktree.patch` stores tracked changes, and safe non-ignored
untracked files are copied. `archiveAgent()` writes `retirement.json` only for

## parse-state.ts priority order (legacy)

## Folder browser (`src/tui/folder-browser.ts`)

Builds the navigable item list for the add-repo folder browser dialog (`A` in `ib watch`). Given a current path, produces a list of `FolderItem` entries: ancestors from root down to parent, the current folder, and sorted child directories. Each item includes depth, git-repo detection (`isGit`: the folder has a `.git` entry, via `hasGitEntry` in `src/create-repo.ts`), and ancestor/current flags for rendering the tree-style UI.

The dialog itself (`folder-browser` in `src/tui/dialog-handler.ts`, wired up by `handleFolderBrowser` in `src/tui/agent-actions.ts`) has the button row `[ Cancel ]  [ New Repo ]  [ Add ]`. `folderBrowserButtons` decides which buttons the selected folder enables, for both the key handler and the renderer: `[ Add ]` needs a git folder that is not registered yet, and `[ New Repo ]` needs a folder that is not a git repo. A disabled button is drawn dimmed, and Tab / Shift+Tab step through `list → Cancel → New Repo → Add` and skip it.

- `[ Add ]` registers the folder under `repoNameFromFolder(basename)` (`src/registry.ts`: lowercase, whitespace → `-`, anything outside `[a-z0-9_-]` dropped). `checkNewRepoEntry` (behind `ib add`, `[ Add ]` and `[ New Repo ]`) refuses a name equal, ignoring case, to a registered repo's name or nickname (SPEC §9.2): registry names key tree rows. Its `nameHint` ends a taken-name refusal: `ADD_NAME_HINT` (`use ib add <path> <name>`) for `addRepo`, `NEW_REPO_NAME_HINT` (`choose another folder name`) for `createRepo`.
- `[ New Repo ]` closes the browser and opens an `input` dialog for a folder name. The input dialog draws its prompt as the title, so `newRepoPrompt` cuts a long parent path from the left (`New repo in …/Developer/bun:`, via `elideLeft` and `dialogTitleMaxWidth` in `dialog-handler.ts`) to keep the title inside the box. On submit, `createRepo(parent, name)` (`src/create-repo.ts`) creates `<parent>/<name>` (no `recursive`, so an existing folder is refused), runs `git init` and `git commit --allow-empty -m "Initial commit"` with the user's own git config, and calls `addRepo`. Before it touches the disk it rejects an empty name, `.`, `..`, a name with `/`, a parent that has a `.git`, and anything `checkNewRepoEntry` (the rules `addRepo` enforces) would refuse. When git or `addRepo` fails after the folder exists, the error names the folder and nothing is deleted. git runs through `createRepoSpawnCtx`; tests give it a throwaway identity with `makeGitIdentity` (`src/test-git-identity.ts`).

On success both paths reload `ctx.repos` from the registry and refresh the watcher (`reloadRepos`).

## Ghostty (`src/ghostty.ts`)

- `openInGhostty(tmuxSession)` spawns Ghostty with `--command=bash -c 'tmux set-option -t <session> window-size latest && tmux attach -t <session>'`, detached via `proc.unref()`. The `window-size latest` prefix makes tmux re-fit to Ghostty's dimensions on attach; the `bash -c` wrapper prevents Ghostty's login shell flags from being passed to tmux. `+new-window` (reuse existing instance) is GTK-only and not available on macOS, so each call spawns a new Ghostty app. Because attaching drops the pinned-width override (the window follows Ghostty while attached), `DashboardComponent.checkClientAttached` re-pins the window to `PINNED_TMUX_WIDTH` on the attached→detached transition so the dashboard reflow assumptions hold again.
- `openPathInGhostty(dirPath)` is the directory-opening counterpart — launches a Ghostty window cd'd into `dirPath` (no tmux attach).
- Validates session name with `/^[\w-]+$/` before interpolating into `--command`.
- Both functions return `{ ok, message }`.

## CLI test isolation (`src/test-cli-runner.ts`, `src/test-cli-driver.ts`)

Tests run the CLI through the runner, in a temporary cwd and HOME with an explicit minimal environment, and through the driver instead of a real entry point. A temporary HOME is not enough on its own: routing identifies the caller from the cwd, and the caller check reads the OS account's registry (`userInfo()`) and the real process ancestry. See `docs/test-isolation-plan.md`.

- **Driver**: installs its guards before loading production modules, because `SpawnContext` captures `Bun.spawn` at module load. Processes, signals and network attempts are logged and thrown; the log is what fails the test, since production sometimes swallows the throw (`tgtyping`). `tmux list-sessions` and `has-session` answer "no server". `isSandboxedProcess()` comes from the test. The real `resolveNoWorktreeCaller` runs against the fixture registry and the test's ancestry, for both the CLI and hook resolvers.
- **`cliActions` (`src/index.ts`)**: the handlers `main()` calls after parsing and routing; the driver's seam. A handler refuses unless the test names it: `"record"` to assert its arguments, `"real"` to run it. Commands outside `cliActions` always run for real under the guards, and their file writes land in the fixture because every path derives from the cwd, HOME or registry.
- **Brokers**: the client stays real. `withFixtureWatchdog` serves a fixture agent's queue with the real `processSpawnRequests` and fake terminal operations.
- **Boundary not covered by the guards**: file writes to an absolute path that ignores the fixture. Production has these only in `src/message-attachments.ts` (send-time staging, not reached by `ib send`), the merge rebase check's `/tmp/ib-rebase-check-*` (after a blocked git call) and `src/hooks/inject-status.ts`'s `/tmp/ib-status-hash-*`.
- **Real entry points**: `runInertEntryPoint` refuses anything that could mutate. `src/cli-isolation.test.ts` has the regression tests, a sweep of every dispatch route against a sentinel "live" agent, the real `sendMessage` writing to the fixture's outbox (the driver does not guard file writes, so a recorded handler cannot show where they land), and checks that no production code reads the driver's config and no test launches an entry point directly.

## Debugging — `ib state`

`ib state` (or `ib state --json`) lists every agent with its tmux pane PID, claude PID, and watchdog PID, plus liveness for each (✓ alive, ✗ dead, — missing). When pane_pid has child processes that aren't the recorded claude_pid, they show as `[orphans: N]`. Implementation: `src/state-command.ts`.

Orphan-process detection recognizes each agent CLI by its argv shape AND a cwd inside a registered repo's `.itsybitsy/agents/…` (argv alone is never enough — a user's own `claude --resume` / `agy --conversation` in a normal terminal must never be flagged). `looksLikeClaudeArgv` (`claude --resume`/`--session-id`) + `isClaudeAgentProcess`, and `looksLikeAgyArgv` (`agy --dangerously-skip-permissions`/`--conversation`/`--log-file`, including disabled launches) + `isAgyAgentProcess`, share the `cwdUnderRegisteredWorktree` anchor. claude and agy processes land in the same `claude_processes` orphan bucket (their PIDs are all tracked under `claude_pid`); the cleanup verify matcher (PID-reuse defense) accepts either.

`ib state` always renders an `ORPHANS` section. Four categories:

- **tmux sessions** — sessions matching `ib-coordinator` (exact) or `itsybitsy-<repoId>-<agentId>` that aren't in any registered repo's tracked set.
- **claude processes** — running `claude --resume <id>` / `claude --session-id <uuid>` whose **cwd is inside an itsybitsy worktree** and whose PID isn't recorded in any tracked agent's `meta.json` `claude_pid`. cwd anchor is critical — a user running `claude --resume <id>` in their own terminal must NEVER be flagged. cwd lookup uses `lsof -d cwd` on macOS and `/proc/<pid>/cwd` on Linux.
- **watchdog processes** — running `ib watchdog <agent-id>` whose PID isn't in any agent's `watchdog_pid`.
- **ib watch processes** — every running `ib watch` (informational; no tracked set).

The tracked set is built from ALL agents in ALL registered repos plus the system coordinator's session.

`ib state --cleanup` kills every orphan: `tmux kill-session` for sessions, SIGTERM then SIGKILL for processes. Safety:
- Tracked set is rebuilt **immediately before** cleanup; any orphan that became tracked between gather and cleanup is skipped.
- Before SIGKILL, each PID's command line is re-resolved via `ps -o command=`; if it no longer matches an itsybitsy pattern, SIGKILL is refused (PID-reuse guard).
- Tmux session names are validated with `isValidTmuxSession` before being passed to `tmux kill-session`.

`ib state --cleanup --dry-run` previews what would be killed. In `--json` mode, `cleanup_actions` is added only when `--cleanup` was passed.

**Known limitation**: if you run both bash `ib` and bun `itsybitsy` without a shared `~/.itsybitsy/repos.json`, `--cleanup` from one install will see the other's watchdogs as orphans.
